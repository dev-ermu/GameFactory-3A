# 游戏UI生成

在准备好的工作区内，生成某个任务的引擎原生UI，以及对应的浏览器端运行版本。UI负责界面展示以及与公开机制的交互绑定；它不负责游戏逻辑规则、浏览器后端、执行过程或结果评估。

## 权限与输入要求

编辑前请仔细阅读以下内容：
- 准备好的UI数据包、需求说明、验收标准、设计/通用要求、界面截图、视口参数、约束条件以及禁止使用的UI元素；
- 流水线系统维护的官方引擎版本及只读的引擎上下文；
- 最终确定的机制相关工件、接口规范、已声明的绑定关系，以及仅限公开的运行时适配器路径；
- 同一引擎下已注册的机制/UI示例根目录、推荐路径、必需的浏览器端运行引用，以及经过验证的浏览器端交接配置；
- 所有提供的参考图片、本技能文档以及引用的提示内容。

权限优先级如下：首先依据最终确定的机制接口规范确定可用的绑定关系；其次参考UI任务需求及验收标准定义行为逻辑；接着参照参考图片完成视觉排版；再依据设计/通用要求明确产品定位；最后参考示例确定实现结构。流水线系统负责引擎的身份认定、边界界定、验证及最终定稿。请勿更改引擎版本，也切勿跨引擎混用API或示例。

这些示例仅为只读的工程参考资料，并非基础插件、模板、脚手架、继承目标、运行时依赖项、类型/风格限制或能力上限。请仅查看已注册根目录下的最小可用子集，切勿扫描整个根目录。同一引擎下的任意示例都可能涉及模块、构建、绑定、测试或原生UI模式的参考；无需寻找类似的游戏玩法或视觉类示例。

## 交付流程

请按顺序生成两个阶段的内容：
```text
1. 引擎原生版本
2. 浏览器端运行版本
```

### 引擎原生版本

在`generated_ui/`目录下，生成真实的HUD、界面、控件、资源、布局、焦点/输入处理逻辑、反馈机制、绑定关系、测试用假数据以及原生测试代码。

1. 查阅对应引擎的API文档。
2. 参考最终确定的机制接口规范，仅使用其中声明的公开适配器路径。
3. 查看最小可用的机制相关及原生UI参考内容。
4. 仅通过公开的机制运行时适配器来查询状态、订阅事件并调用命令。
5. 实现所有必需的界面及状态，包括相关的HUD、上下文提示、菜单、标签页、列表、对话框、加载/空状态/禁用状态/成功/错误状态、焦点切换，以及事件/命令反馈逻辑。
6. 生成绑定清单以及用于原生测试的模拟机制假数据。

一个接口规范可能驱动多个界面，但UI代码不得复制机制接口规范内容、自行创造绑定关系、强制转换为具体的游戏逻辑类、访问私有的生产者类型、重新实现游戏规则，或维护第二套游戏状态存储。

### 浏览器端运行版本

在以下路径下生成该任务专属的浏览器端运行源代码及测试代码：
```text
generated_ui/browser_play/
```

请将浏览器服务端API、已注册的功能特性、必需的浏览器端运行示例，以及仓库中已有的玩家前端代码作为只读参考。该页面必须：- 浏览器服务健康检查；
- 恢复指定的会话或创建通用会话；
- 调用引擎中立的`stream_url`；
- 在流式传输的引擎画面内保持键盘/鼠标焦点；
- 准确呈现启动中、就绪和错误三种状态；
- 提供任务所需的流/会话控制功能以及通用输入处理逻辑。

切勿依赖未文档化的外部页面来创建首个会话。
引擎流中已包含原生游戏UI。浏览器播放模块不得复制HUD、占用Mechanic绑定逻辑、实现游戏指令、自行管理传输层、根据引擎名称做分支判断，也不得生成或修改`EngineBackend`。已注册的后端负责处理特定传输层的URL准备工作。

使用`gamefactory3a.browser_play_manifest.v1`以及引用的轻量级任务专属启动脚本，生成`browser_play_manifest.json`。该脚本可以设置文档中规定的浏览器服务环境变量，并调用`python -m engine_adapters.browser_serving`；但绝不可实现、复制或导入具体的后端类。这是唯一被允许的过程生命周期例外情况。

## 视觉规则

逐一检查所有提供的参考图像。在进行视觉相似性比对前，需先应用任务要求与禁用UI规范；利用图像来确定层级、密度、间距、颜色、排版和风格。优先遵循优先级更高的约束条件，并上报材质偏差情况。

应生成完整的交互状态，而非仅包含截图的外壳。原生UI负责游戏画面的呈现，浏览器播放模块仅负责内容传输、流/会话控制以及通用的浏览器交互功能。

## 输出、来源与测试

任务专属的必需输出包括：
- 位于`generated_ui/`下的引擎原生UI源文件/资源及原生测试代码；
- 位于`generated_ui/browser_play/`下的浏览器播放模块源文件/测试代码；
- `generated_ui/ui_binding_manifest.json`；
- `generated_ui/Tests/fixtures/mechanic_contract_fixture.json`；
- `generated_ui/screenshot_plan.json`；
- `generated_ui/context_used.json`；
- `generated_ui/browser_play/browser_play_manifest.json`及其启动脚本。

`context_used.json`采用`gamefactory3a.context_used.v1`格式，其中记录了：
- 对应阶段为`engine_native`的匹配引擎API；
- 对应阶段为`browser_play`的浏览器服务API；
- 作为`browser_play_example`的必需浏览器参考内容；
- 仅作参考的Mechanic/UI路径，如`mechanic_example`或`ui_example`；
- 每个示例条目中至少包含一个被允许的工程`purpose`。

仅记录属于本仓库、被允许且同引擎相关的上下文。不得记录仅限根目录访问的内容、未被引用的路径、无关上下文，或其他任务生成的输出结果。

原生测试使用模拟的Mechanic测试数据，覆盖绑定逻辑、状态、布局、交互、焦点及必需界面等内容。浏览器测试使用浏览器服务测试数据，绝不调用Mechanic测试数据。若缺少必需的行为表现，测试必须判定为失败；需避免空断言或无条件的成功结果。

## 边界与归属- 仅需在指定的工作区内编写内容，且任务相关的输出需存放在 `generated_ui/` 目录下。
- 数据包输入、引擎上下文、示例、机制相关产物、参考图片、技能、提示词以及框架前端内容均视为只读项。
- 切勿查看、对比、复制或复用 `<REPO_PATH>/test_data/outputs/` 目录或其他指定输出路径下其他任务或游戏生成的实现代码。
- 切勿修改机制相关源码、流水线元数据、框架后端或仓库自带的浏览器服务端前端。
- 切勿创建替代性合约、虚构的绑定逻辑、回退状态存储、运行时模拟器/提供者、`generated_adapters/` 目录、后端工厂、流传输模块或引擎输入注入逻辑。
- 切勿执行生成的启动程序；该操作属于后续的执行阶段。
- 切勿调用仅用于执行/评估的 API、启动引擎、截取/伪造截图、削弱测试内容，或宣称构建/可玩性/基准测试结果达标。

各模块职责划分如下：
- 智能体负责引擎原生 UI、浏览器播放功能、清单文件、测试用固定数据、生成的测试代码以及UI相关的修复工作；
- 机制模块负责游戏玩法规则、状态/事件/命令及其公开适配器；
- 浏览器服务端负责后端注册、数据传输、流URL准备以及引擎集成工作；
- 代码生成流水线负责数据包、边界定义、快照、定稿流程以及发布元数据；
- 执行/评估模块负责权威性的构建/测试、渲染、截图、运行时证据、浏览器冒烟测试以及评分工作。

## 运行与发布合约
运行是最小的可复现发布单元：
```text
任务数据包 -> UI 生成（引擎原生 + 浏览器播放）
            -> 定稿后的 UI 工作区 -> 评估
```
每个产物均通过 `(game_id, run_id, task_kind, task_id)` 标识，并存放于 `<REPO_PATH>/test_data/outputs/README.md` 中描述的对应游戏的共享输出树内：
```text
test_data/outputs/<game_id>/
|-- latest -> <run_id>/             # 指向最新运行的符号链接
`-- <run_id>/
    |-- run_meta.json               # 运行溯源信息，由流水线模块负责维护
    |-- ui_results_summary.json     # 由流水线模块负责维护
    |-- ui/<task_id>/               # 指定的 UI 工作区
    `-- eval/ui/<task_id>/          # metrics.json，由流水线模块负责维护
```
上述路径由 `<REPO_PATH>/pipeline/common/paths.py` 统一管理，请勿手动构造。流水线会预先准备好 `ui/<task_id>/` 目录并将路径传递给智能体；智能体仅需在该工作区内写入内容。

UI 工作区的结构如下：
```text
ui/<task_id>/
|-- meta.json       # 由流水线模块维护的身份与状态信息
|-- generated_ui/   # 所有任务相关的 UI 输出（参见“输出、溯源与测试”部分）
`-- demo_outputs/   # 由流水线模块负责维护，为预留目录
    |-- code_gen/   # task_packet.json · instructions.md ·
    |               # workspace_snapshot.json · finalize_result.json
    `-- repairs/attempt_NN/  # 用于第N次修复尝试的重备数据包
````generated_ui/`目录下的引擎原生UI会沿用对应引擎自身的布局规则——例如Unreal中的`Plugins/GameUI/`，Unity中的`Assets/UI/`，Godot中的`addons/game_ui/`，或是Three.js中的`src/components/`——因此上层代码绝不能默认其为Unreal引擎的布局。框架浏览器相关的代码绝不会被拷贝到游戏产物中。务必将`Binaries/`、`Intermediate/`、`Saved/`、派生数据缓存、`__pycache__/`以及其他可变输出文件排除在工作区之外。

`meta.json`、`demo_outputs/`和`evaluation/`属于预留目录：绝对不能创建、修改或删除它们。`workspace_snapshot.json`记录了工作区内每个文件的SHA256哈希值及大小，这些文件被分为`task_files`和`protected_files`两类；工作区定稿时会重新生成清单文件，若检测到对受保护路径的更改则会拒绝定稿，同时会报告该任务相关的差异内容。

已发布的工作区是不可变的。若出现结构化故障，系统会触发修复流程：流水线会重新准备同一个工作区，并将故障相关信息及之前的结果存入`demo_outputs/repairs/attempt_NN/`目录下，此时智能体仅会修改属于UI部分的源代码、清单文件、测试用假数据和测试用例。全新启动时会使用新的`run_id`，且绝不会覆盖已发布的运行记录。评估流程会在`eval/ui/<task_id>/`目录下对定稿后的工作区进行评分，并将结果记录在`metrics.json`文件中。

仅定稿操作会写入`ui_results_summary.json`，更新`run_meta.json`，并重新指向`latest`；只有流水线才会更新`meta.json`中的状态。定稿后的工作区仅能证明生成过程已完成——源代码生成、静态验证或产物存在性检查均不能等同于具备可玩性；只有执行结果与评估结果才能作为可玩性的依据。

## 修复与收尾

针对结构化故障，需找出最小的、属于UI层面的根本原因，同时保留以下要素：引擎的标准规范、机制合约/版本要求、仅通过公共适配器访问的规则、来源追溯信息、空的浏览器机制绑定、已注册的后端依赖关系、浏览器后端与前端的分离架构、无关的正常运行行为，以及故障相关证据。修复时仅修改属于UI部分的源代码、清单文件、测试用假数据和测试用例，不得改动游戏玩法或削弱测试用例的有效性。

需上报的内容包括：发生变更的文件、覆盖的界面/评判标准、被调用的机制绑定、参考图像的偏差情况、原生/浏览器测试覆盖率、未解决的风险点，以及缺失的输入项。切勿上报关于渲染效果、构建结果、测试结果、可玩性或基准测试是否达标的信息。
