# 游戏机制生成

在准备好的工作区内生成某个任务所对应的游戏机制实现。该实现包含游戏玩法行为以及与展示形式无关的公开接口；它不包含用户界面、执行逻辑或评估功能。

## 权限与输入

编辑前请阅读以下内容：

- 准备好的任务包、任务要求、验收标准以及可选的一般性要求；
- 生成的资源与动作描述符；
- 引擎管线提供的标准引擎标识符及只读的引擎上下文；
- 已注册的同引擎机制示例根目录以及任务建议的路径；
- 本技能说明及引用的提示内容。

权限优先级依次为：任务包与要求、本技能说明、匹配对应引擎的API，最后是示例。请准确选择一种非空的、与标准引擎匹配的引擎API。切勿更改引擎类型、混用不同API，或在缺少对应文档时自行创造API。

示例仅用于演示同引擎API的使用方式、模块/插件结构、构建配置、公共适配器设计以及原生测试模式。请选取最小且可用的示例集，其中至少包含一个位于允许的根目录下的文件或插件目录；默认情况下切勿扫描整个根目录。示例并非基础代码、模板、继承目标、脚手架、运行时依赖项、类型限制或能力上限。任何同引擎类型的示例均可用于讲解结构。
无需强制要求有对应的示例。

## 工作流程

1. 检查工作区内容，保留与当前任务相关的已有工作成果。
2. 将每条验收标准对应到生成的源代码、可观测的行为表现、接口状态/事件/命令，以及至少一项有意义的原生测试。
3. 将界面表述转化为机制信号。例如，生命值条需要反映当前/最大生命值状态；胜利画面需要体现胜利状态/事件；重新开始按钮需要触发重新开始命令。
4. 查阅匹配的引擎API以及最小可用示例参考。如果任务涉及音频、视频CG、动画CG或特效触发，需使用对应引擎API中的**Media Director**部分。
5. 设计适合该任务的、内部模块化的架构，不得直接使用或修改框架适配器的内部实现。
6. 仅通过提供的描述符来调用生成的输入数据。
7. 生成游戏玩法源代码、构建/配置文件、原生测试代码、公共运行时适配器，以及任务所需的启动/重放/追踪相关源码。
8. 在工作区根目录下发布`mechanic_contract.json`和`context_used.json`文件。
9. 定稿前需逐一核对所有验收标准、确定性/可重放性要求、产物、接口条目以及测试结果。

## 范围与架构一个Mechanic任务可以实现一个完整的可玩垂直切片，其中包含多个并非每个示例都具备的系统，比如交互、捕获、队伍管理、任务系统、物品栏、对话、战斗以及存档相关状态。复杂的系统应通过统一的公共运行时适配器进行模块化处理。不要强行将该任务的类型或架构套用到某个示例上，也不要在验收标准仅要求实现较小规模垂直切片时，就宣称其能打造出商业级游戏。

依赖关系如下：

```text
UI -> Mechanic -> 运行时框架
```

严禁出现反向依赖。Mechanic必须能够在没有UI模块、HUD、控件、菜单、渲染器或截图的情况下完成编译、测试和评估。切勿生成UMG、Slate、Canvas、准星、进度条、遥测数据、视觉布局、样式、反馈信息，也不得指定具体的游戏HUD。

## Mechanic契约

需发布符合`schema gamefactory3a.mechanic_contract.v1`规范的`mechanic_contract.json`文件。

| 字段 | 要求 |
|---|---|
| `contract_version` | 公开的、为正数的契约版本号 |
| `gameplay_module` | 生成的、归属于游戏项目的模块的确切名称 |
| `state` | 暴露给UI的非空可观察值 |
| `events` | 非空的游戏玩法转换/通知信息 |
| `commands` | UI或运行时可调用的非空操作 |
| `public_api_paths` | 指向生成的适配器源代码的、非空的工作区相对路径 |

这些条目必须代表真实生成的行为，而非占位符。该适配器必须支持状态查询、事件订阅和命令调用，同时不能暴露私有的Pawn、Character、Controller或实现类。内部系统即便发生变化，也不得改变面向UI的依赖方向。

## 输出、来源说明与测试

仅生成属于该任务自身的产物：
- 引擎原生游戏玩法源代码及引擎原生游戏玩法测试源代码；
- 公共运行时适配器源代码；
- `mechanic_contract.json`和`context_used.json`；
- 所需的构建/配置文件以及启动/回放/追踪源代码。

切勿生成或修改预置的数据包、工作区快照、`meta.json`、`demo_outputs/`目录下的内容、评估产物、权威报告、基准测试分数或Pipeline结果元数据。

`context_used.json`需遵循`gamefactory3a.context_used.v1`规范，且必须记录以下内容：
- 与仓库匹配的对应引擎API；
- 仅限允许范围内的同引擎示例根目录下的实际被引用路径；
- 示例角色为`mechanic_example`；
- 每个示例条目至少包含一种允许的工程用途。

切勿记录仅涉及根目录的访问记录、无关上下文、跨引擎路径或其他任务生成的输出内容。

生成的测试是修复行为的佐证，而非基准测试的权威依据。当所需行为缺失或不正确时，测试必须失败；测试需涵盖可观察状态的转换及配置值的验证，并给出有用的诊断信息。应避免空断言、无条件成功、仅检查构造过程的断言以及仅基于常量值的断言。绝不可为了掩盖修复后的问题而削弱、删除、跳过或更换失败的测试。

## 边界与所有权- 仅需在预设的工作区内写入内容。
- 将任务输入、描述符、技能、提示词、引擎上下文、示例以及最终的上游产物视为只读内容。
- 仅可使用所选引擎API中已文档化的公共接口。
- 进行媒体集成时，需遵循规范的`media_director`/`A3GameMediaDirector`命名约定，并保留原生文件命名规则；切勿创建并行的`MediaManager`或`CutsceneManager`相关组件。
- 不得导入、复制或修改适配器内部逻辑；不得自行编造资源路径；不得绕过描述符直接操作；不得继承示例游戏玩法类、复制示例游戏玩法代码，或在运行时依赖示例插件。
- 不得查看、对比、复制或改编`<REPO_PATH>/test_data/outputs/`目录或其重定向输出根目录下其他任务或游戏生成的实现代码。
- 机制模块不得依赖用户界面，也不得通过转换为私有/偶然的运行时类型来暴露面向用户界面的状态。
- 不得调用仅用于执行/评估的API，不得运行权威性测试，不得启动引擎，不得评定基准分数，也不得宣称构建/可玩性达标。

所有权划分如下：
- 智能体负责游戏所属的机制模块源代码、生成的测试代码、契约以及修复变更内容；
- 代码生成流水线负责任务/上下文组合、提示词渲染、边界设定、数据包处理、快照生成、定稿以及元数据管理；
- 执行/评估环节负责引擎准备、资源导入、权威性构建/测试、运行时证据收集、截图生成以及基准评分。

后续进行资源导入时，执行过程必须通过所选公共引擎API解析提供的描述符，为当前任务复用已配置的引擎客户端/会话，在会话边界处检查准备情况，并保留结构化的结果与日志。仅当引擎API有相关说明时，仓库启动器才可管理生命周期。仅依靠导入或映射加载成功并不能证明资源具备可玩性。

## 运行与发布契约
运行是最小的可复现发布单元：
```text
任务数据包 -> 机制模块生成 -> 定稿的机制模块工作区 -> 评估
```
每个产物均通过`(game_id, run_id, task_kind, task_id)`标识，并存放于`<REPO_PATH>/test_data/outputs/README.md`中描述的各游戏共享输出树内：
```text
test_data/outputs/<game_id>/
|-- latest -> <run_id>/                 # 指向最新运行的符号链接
`-- <run_id>/
    |-- run_meta.json                   # 运行溯源信息，由流水线负责维护
    |-- mechanic_results_summary.json   # 由流水线负责维护
    |-- mechanic/<task_id>/             # 预设的机制模块工作区
    `-- eval/mechanic/<task_id>/        # metrics.json，由流水线负责维护
```
这些路径由`<REPO_PATH>/pipeline/common/paths.py`统一管理，切勿手动构造。流水线会预先准备好`mechanic/<task_id>/`路径并将它交给智能体；智能体仅需在该工作区内写入内容。

机制模块工作区为：```text
mechanic/<task_id>/
|-- meta.json                # 流水线拥有的身份信息及状态
|-- mechanic_contract.json   # 由Agent在工作区根目录发布
|-- context_used.json        # 由Agent在工作区根目录发布
|-- launch*                  # 任务所需的启动/回放/追踪源文件
|-- project/                 # 引擎原生游戏逻辑源码、适配器及测试文件
`-- demo_outputs/            # 流水线所有，预留专用
    |-- code_gen/            # task_packet.json · instructions.md ·
    |                        # workspace_snapshot.json · finalize_result.json
    `-- repairs/attempt_NN/  # 用于第NN次修复尝试的重备数据包
```

引擎原生的项目会保持该引擎自身的目录结构——例如Unreal中的`Plugins/GameMechanic/`，Unity中的`Assets/Mechanics/`，Godot中的`addons/game_mechanic/`，或是Three.js中的`src/mechanics/`——因此上层代码不应默认以Unreal引擎为准。需将`Binaries/`、`Intermediate/`、`Saved/`、派生数据缓存、`__pycache__/`及其他可变的引擎输出文件排除在工作区之外。

`meta.json`、`demo_outputs/`和`evaluation/`属于预留目录：切勿创建、修改或删除它们。`workspace_snapshot.json`记录了工作区内每个文件的SHA256哈希值及大小，这些文件被分为`task_files`和`protected_files`两类；最终定稿时会重新生成清单，拒绝更改受保护路径的操作，并报告该任务相关的差异内容。

已发布的工作区是不可变的。若出现结构化故障则会触发修复流程：流水线会在`demo_outputs/repairs/attempt_NN/`目录下，用故障摘要及先前结果重新准备相同的工作区，而Agent仅修改游戏专属的源码及测试文件。全新任务会使用新的`run_id`；已发布的运行记录绝不会被覆盖。评估流程会在`eval/mechanic/<task_id>/`目录下对最终定稿的工作区进行评分，并在该处生成`metrics.json`文件。

仅最终定稿环节会写入`mechanic_results_summary.json`，更新`run_meta.json`，并重新指向`latest`；只有流水线才会更新`meta.json`中的状态。最终定稿的工作区仅能证明代码已生成——静态代码生成或 artifact 存在性检查不能等同于可玩性验证；唯有执行结果及评估证据才能作为有效依据。

## 修复与完成

针对结构化故障，需找出最小的根因，仅修改游戏专属的源码/测试文件，保留规范的引擎版本、合约、溯源信息、无关的正常行为表现以及故障相关证据，且不得削弱测试用例。

需上报变更的文件、验收标准的覆盖情况、生成的测试覆盖率、未解决的风险以及缺失的输入项。需返回源码变更内容及诊断信息；切勿上报关于构建、测试、可玩性或基准测试是否成功的权威性结论。
