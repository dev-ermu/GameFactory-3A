# 任务跟踪

每个游戏项目需维护一份结构化的任务列表。让模型直接读取该列表，同时让生成页面显示相同的状态；切勿分别维护仅模型使用的清单和仅页面使用的清单。

## 最小任务记录

| 字段 | 用途 |
|---|---|
| `id`、`title` | 稳定的标识与具体产出 |
| `parent_id`、`chapter_id`、`beat_ids` | 所属章节/剧情节点以及功能分组 |
| `requirement_ids`、`asset_ids`、`screen_ids` | 追溯至需求行为及章节资源 |
| `stage` | 流程阶段：剧情/设计、资产制作、机制开发、UI设计、组装或验证 |
| `design_revision` | 该任务所实现的设计版本 |
| `depends_on` | 前置任务的ID |
| `owner` | 负责该任务的智能体或人员 |
| `inputs`、`outputs` | 指向需求文档、合同及产物的引用 |
| `acceptance` | 任务完成的可观测判定条件 |
| `status`、`blocker` | 当前状态及无法推进的原因 |
| `evidence` | 根据情况填写测试报告、构建文件、截图或回放链接等佐证材料 |

具体的任务记录与设计文档应存储在游戏专属的任务工作区中，而非存放在`agent_skills`里。复用现有的项目路径规范。本文档仅作为操作协议；无需假定存在特定的存储服务或页面API。

## 状态流转规则

采用`needs_detail → ready → in_progress → review → done`的流程，若遇到未解决的前置依赖、缺失的输入资料或执行失败情况，则标记为`blocked`。

- 仅当输入资料、验收标准及依赖关系均满足时，才能标记为`ready`。
- 开始工作前需先明确任务负责人；避免多人同时编辑同一文件造成冲突。
- 记录好输出成果及验证佐证后，方可转入`review`状态。
- 只有当任务的验收标准全部通过时，才能标记为`done`。若未达标，需记录相关问题并退回`in_progress`状态；若根本无法继续推进，则标记为`blocked`。
- 一旦设计或合同发生变更，需重新打开受影响的任务。重新核查下游产出结果，而非直接采信旧版本的佐证材料。

将生成、组装及验证过程拆分为独立的任务处理。绝不能仅仅因为源文件或素材已生成，就认定该片段可正常运行。只有当前所有子任务均完成且端到端运行验收通过后，才能标记父里程碑为完成。

## 模型与页面行为准则

处理每个任务前，需读取其所属章节的目标、相关剧情节点、当前记录、素材/画面引用、依赖结果及最新的阻塞因素。任务执行完毕后，在选取下一个就绪任务前，需先更新输出成果、佐证材料及状态。按章节对工作台内容进行分组，标明哪些素材是新增的、可复用的或仍缺失的；同时将叙事播放顺序与并行生产调度分开展示。

在生成工作台中显示任务树、当前工作内容、阻塞因素及佐证链接。通过同一份权威记录同步更新数据。在该集成功能完善前，需手动更新项目记录并说明界面同步偏差；切勿宣称页面已同步，也不得要求通过截图来恢复任务状态。
