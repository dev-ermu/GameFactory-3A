# 交互与展示设计

将交互机制与面向玩家的展示内容统筹设计，并在不同层级中分别实现。应将UI视为游戏体验的一部分，而非规则设定完成后再添加的装饰。

## 定义完整的交互流程

针对每个功能，需明确以下内容：
- **意图**：玩家的需求以及该操作如何被玩家发现。
- **规则**：操作的前提条件、有效动作、成本及结果。
- **输入**：触发方式、目标选择、确认/取消操作以及中断机制。
- **状态**：根据需求定义不可用、就绪、激活、成功、失败及恢复等状态。
- **反馈**：每种状态转换时对应的场景提示、HUD、摄像机效果、动画、音效及视觉特效。
- **可接受性**：玩家如何理解、完成并重复该交互流程。

将每个可交互的UI元素对应到所需的指令，将每个显示元素对应到所需的状态或事件。需明确禁用状态和错误状态下的表现；避免出现无任何功能的装饰性按钮。

## 确立统一的视觉风格

明确屏幕层级、布局、排版、配色、间距、动效及视觉参考标准。让UI与游戏世界、摄像机及反馈时机相协调。有意识地区分世界空间提示与屏幕空间提示。除非游戏确实需要，否则不要在玩家体验中加入通用的仪表盘布局或调试面板。

需整体审视交互流程，而非仅看静态截图。还需考虑视口适配、文字可读性、焦点管理、输入捕获以及相关无障碍需求。

## 用于白盒生成的语义化颜色

当物体的功能或会影响玩家决策的属性存在显著差异时，应选用不同的纯色：例如资源节点与生产建筑、侦察单位与重型单位、物理类装备与元素类装备之间应区分用色。无需为细微的数值差异单独分配独特的色调。

在项目本地创建图例文档，记录`semantic_id`（语义ID）、`meaning`（含义）、`color`（颜色）、`secondary_cue`（次要提示）、`applies_to`（适用范围）及`visibility`（可见性）等信息。将相关资产与对应的语义ID关联起来；在世界场景占位符、角色列表缩略图、装备查看界面及属性徽章中均采用同一映射关系。该图例应与游戏设计文件一同保存，而非作为覆盖所有游戏类型艺术配色的通用规则。- 对于非交互式的环境几何体，应使用中性、低对比度的颜色。
- 选用数量较少且区分度明显的功能配色方案。当存在多个阵营或类别时，应结合轮廓、图案、符号和文字来区分，而非依赖14种细微差异的色调。
- 分离视觉通道：模型使用功能性着色，所属关系通过圆环或横幅体现，临时状态用轮廓或图标表示，选中状态则采用独立的高亮效果。切勿让一种颜色承载相互矛盾的含义，也不要重复使用预留的视觉提示。
- 显著的色彩差异需搭配非色彩类的提示信息。需检查颜色与场景背景的对比度，以及在实际摄像机距离和UI尺寸下的可读性。
- 遵循可发现性和可见性规则。隐藏的感染状态、伪装或未公开的属性不得改变玩家可见的颜色；仅用于开发人员的诊断图层必须独立呈现并标注清楚。
- 具体数值应显示在详情面板中。类别颜色不能替代统计数据，也不能用来暗示稀有度、所属关系或是否已解锁/装备。
- 最终美术资源到位后，需替换原型材质，同时保留重要的视觉提示。

在验收白盒版本前，需在游戏场景和资产展示页面中验证配色映射是否正确。这些规则用于指导设计，并不意味着现有的预览图会自动采用语义ID或实现诊断图层。

## 选择并调整JSON布局

直接从`agent_skills/game_design/game_layout_templates/`目录下读取对应类型的模板文件，无需单独的目录表。文件名按`<类型>_<屏幕>`的规则命名，绝不能使用游戏标题、系列名称或角色名。
- `agent_skills/game_design/game_layout_templates/rts.json`：适用于即时战略游戏，包含等轴测世界视图、资源栏，以及底部停靠栏（内含迷你地图、角色头像、单位属性、背包和指令按钮）。
- `agent_skills/game_design/game_layout_templates/action_rpg.json`：适用于动作角色扮演游戏，采用后方第三人称视角，画面中心无遮挡，左下角显示生命值/物品信息，右下角显示技能栏；仅在触发战斗时才会显示战斗进度条。

每种类型都包含`login`（登录页）、`in_game`（游戏内界面）、`roster`（角色列表页）和`equipment`（装备页）。角色列表页和装备页应专门用于供玩家查看资产，而非生产资产管理。单位档案和模块化装备配置可使用`rts_roster`/`rts_equipment`，全身角色和背包对比则使用`action_rpg_roster`/`action_rpg_equipment`。

登录页应设计为带有背景环境的游戏入口/标题屏，包含继续游戏、开始新游戏、设置选项以及可选的账号登录入口。离线单人游戏不应强制要求填写网站登录表单。设计时可参考同类游戏的空间层级和交互模式，而非其品牌美术风格或名称。类型仅为设计的起点，并非最终美术风格的限制。需将摄像机、地形、建筑、玩家/单位轮廓以及用户界面统一进行设计。切勿用故事板、章节仪表盘或制作待办清单来替代游戏场景；在动作类游戏中要突出世界的主导地位，同时为需要战略单位控制的场景预留稳定的指令空间。

针对每个章节，需记录屏幕信息，包括`screen_id`、`chapter_ids`、`beat_ids`、`template_id`、进入/退出条件、内容以及所需的契约绑定关系。不同环境和状态下的章节可复用同一类型布局。

每个类型文件会定义属于自己的1600x900参考画布。`rect`表示以百分比为单位的`[x, y, 宽度, 高度]`；`layer`用于控制图层的堆叠顺序。类型文件中会包含调色板、场景构成以及用户界面区域。`protected_view`用于保留世界的可见性。`visible_when`用于指定预览标识，比如`combat`。预览中`action`区域的内容仅用于本地演示，绝不能作为游戏逻辑或身份验证代码。在正式契约确立前，需将`required_bindings`视为设计要求。

制作最终美术作品前需先审核纯色构图：要保护世界视图的完整性，优先突出当前目标与动作，确保文字清晰可读，防止控制元素相互重叠。实现时要将示例内容替换为章节专属内容；上线前需确认键盘焦点状态以及不可用/错误状态是否正常。预览功能会对参考画布进行缩放，但这并不能证明布局已适配移动端。若需支持移动端，需单独设计布局并测试真实目标视口。

## 角色与装备检查清单

- [ ] 提供通往角色档案和装备界面的明确入口。
- [ ] 通过资源ID关联浏览器选择区、全身/物体查看器以及详情面板。
- [ ] 合理呈现大型、固定安装、飞行及非实体类资产；切勿强行将所有实体都纳入人形肖像展示范畴。
- [ ] 明确标注搜索/过滤结果、无结果提示、未知状态、锁定状态、不兼容状态以及模型缺失状态。
- [ ] 展示单位的基础属性与生效属性及其来源；仅披露经授权的信息。
- [ ] 隐藏感染状态、伪装的所有权信息以及未探索的敌方数据，这些内容不得出现在公开的检查绑定关系中。
- [ ] 对同一拥有者的兼容插槽进行对比；切勿想当然地认为属性提升就一定有益。
- [ ] 将查看、对比、装备、招募、购买和解锁视为彼此独立的操作。
- [ ] 仅在游戏机制有需求时才添加可选的同伴或装配插槽。
- [ ] 为真实模型查看器指定适应边界、重置、缩放以及可选的轨道控制功能。当前预览使用的是标注清晰的2D轮廓，并非加载的3D资产。

`inspection_samples`仅包含通用的布局模板。需通过单独的授权数据适配器导入实际项目数据；切勿将示例数值当作源游戏的平衡数据。只读预览功能不得宣称已保存装备或阵营变更信息。

## 严守实现边界保持“UI → 逻辑模块 → 运行时框架”的结构。让逻辑模块负责规则与标准状态；让UI负责布局、反馈以及公共绑定。对于缺失的绑定，应提出契约变更请求，而非另建一套游戏玩法状态存储机制。

将生成工作台中的章节/TODO面板与游戏的HUD及菜单分开。让Browser Play专注于会话管理和流媒体传输，而非重新创建引擎原生的HUD元素。在工作台中显示章节进度、资源就绪情况以及受阻任务，而非将其作为游戏内的调试信息展示。
