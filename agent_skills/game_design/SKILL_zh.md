# 游戏设计

将提供的需求和脚本转化为可玩的剧情以及按时间顺序排列的章节计划。假设引擎选择和顶层路由已确定；此处重点聚焦于“发生什么”、“何时发生”以及“每个章节需要什么”。

## 设计流程

1. 从需求说明和脚本中提取所需的体验内容、剧情事实、约束条件和待解决问题。保留稳定的需求/情节节点ID以确保可追溯性。
2. 使用`agent_skills/game_design/narrative_design.md`撰写或改编剧情。保留给定的既定设定；将新增的剧情内容标注为提议内容，而非假装是用户提供的。
3. 借助`agent_skills/game_design/decomposition.md`，按照预估游玩时间和虚构剧情时间来规划章节。为每个章节设定玩家目标、有序的情节节点、进入/退出条件以及明确的分支指向。
4. 推导每个章节所需的人物、场景、道具、动作、音频、视觉特效及UI需求。一次性定义共享素材，并在各章节中引用它们。
5. 使用`agent_skills/game_design/interaction_design.md`以及`agent_skills/game_design/game_layout_templates/`中的类型JSON文件，明确各章节的界面和交互状态。应根据玩家行为来选择或调整布局，而非仅挑选最容易填充的模板。
6. 借助`agent_skills/game_design/task_tracking.md`，将当前章节转化为可追踪依赖关系的任务。在详细规划后续章节前，先生成、整合并运行完整的游戏循环。根据实际游玩情况调整剧情和任务依赖关系。

## 各类游戏类型的素材展示方式

玩家可见的素材展示页面应置于对应类型的模板内，与登录界面及游戏内布局放在一起；无需单独创建专门的类型页面或制作控制台。

- `agent_skills/game_design/game_layout_templates/rts.json`：用`rts_roster`展示单位/英雄，用`rts_equipment`展示装备、同伴及模块化套装。
- `agent_skills/game_design/game_layout_templates/action_rpg.json`：用`action_rpg_roster`展示角色/形态，用`action_rpg_equipment`实现背包查看及装备兼容性对比功能。

通过素材ID关联列表、模型预览和属性信息。将查看功能与装备、招募或解锁功能分开；对无法使用的模型要如实标注。

## 白盒可读性在白盒原型制作阶段，对于功能或玩法属性差异较大的物体，应优先为其选用辨识度高且色调统一的纯色，而非使用毫无区分度的白色或灰色场景。在搭建原型前需先定义颜色与含义的对应规则，并在场景、缩略图及资源查看器中复用该规则。需遵循`agent_skills/game_design/interaction_design.md`中规定的语义色彩规则。要将颜色与标签、图标或轮廓搭配使用；确保阵营归属和临时状态能与功能类别明确区分。在面向玩家的视图中，绝不能通过诊断性颜色泄露隐藏信息。需将这些颜色视为原型阶段的沟通辅助工具，而非强制要求的最终美术风格或实际实现的渲染功能。

## 逐项强制审查
请明确列出各项需求、章节、资源、界面及任务。参照`agent_skills/game_design/decomposition.md`中的检查清单逐一审查每项内容，记录其状态、佐证/参考依据以及未解决的问题。切勿用“所有内容均已覆盖”这类笼统表述替代逐项确认。在确定某章节设计就绪前，需先补全下一章节缺失的项。

## 最低限度的设计交接要求
需提供简短的背景设定与剧情概要、章节时间线、共享资源目录、各章节对应的资源/界面引用，以及下一章节的可执行任务。每一项关键情节都必须对应玩家行为、可见反馈以及验收标准。需确保场景、物品栏、角色认知及未完成任务之间的连贯性。

游戏玩法与呈现效果需协同设计但分开实现：`UI -> 机制 -> 运行时框架`。在设计文档中出现的绑定名称，在相关机制合约正式发布前均视为硬性要求。

游戏相关的剧情、章节规划及待办事项状态应存储在游戏的工作区中，而非存储在本技能模块内。类型JSON模板属于可复用的设计数据；其预览内容仅为示例，并非已生成的游戏，也不代表关联的生成服务。
