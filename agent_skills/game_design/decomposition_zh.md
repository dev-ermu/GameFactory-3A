# 章节、资产与生成任务

按照玩家的时间线体验来划分，而非仅依据资产类型。先粗略规划完整的章节流程；在生成前细化下一章节或可游玩片段的内容。一个章节可能包含多个可测试的片段。

## 1. 梳理需求与剧情节点

为需求和剧情节点分配稳定的ID。标记每一项内容是必需的、可选的还是提议中的。将每项必需内容对应到具体章节及验收条件。标注出矛盾点和缺失的过渡环节；绝不要悄无声息地忽略某个剧情节点。若需要编写或改编故事，请参考`agent_skills/game_design/narrative_design.md`。

## 2. 构建章节时间线

为每个章节记录以下信息：

| 字段 | 必需的设计决策 |
|---|---|
| `id`、`order`、`title` | 稳定的标识以及默认游玩顺序 |
| `requirement_ids`、`beat_ids` | 该章节存在的理由 |
| `play_time_minutes` | 默认游玩流程中的预估起始/结束时间范围 |
| `story_time` | 虚构世界中的时间；需区分闪回和时间跳跃情节 |
| `entry_conditions` | 所需的先前游戏结果、物品及知识条件 |
| `goal`、`beats` | 有序的流程：场景铺垫、玩家操作、探索发现及最终回报 |
| `mechanics` | 新增或复用的交互机制及难度递进规则 |
| `exit_conditions`、`next` | 章节完成条件、分支判定逻辑及目标章节ID |
| `retry`、`checkpoint` | 失败后的恢复机制以及重试时保留的游戏状态 |
| `asset_refs`、`screen_refs` | 该章节运行所必需的所有资产及界面引用 |
| `acceptance` | 可玩性、叙事性、视觉表现及技术层面的验收标准 |

请将游玩时间范围视为估算值，而非强制的过场动画计时器。为各分支设定独立时长，并明确其交汇点或结局；切勿将互斥的分支混在一起。要确保章节边界处的游戏状态保持一致。对于非叙事类游戏，可使用轮次、会话或进度阶段来替代强行设定的剧情线。

## 3. 生成各章节的资产清单

遍历每个剧情节点，确认玩家能看到、能操控及能听到的内容。仅在对应剧情节点有需求时，才纳入角色、环境、道具、动画、视觉特效、音频、UI图形及过场动画等内容。

为每项资产分配稳定的ID、类型、用途、首次出现的章节、所涉及的剧情节点、来源途径（`generate`、`reuse`、`licensed`或`procedural`）、风格约束、变体、依赖项及验收标准。复用现有资产时需记录其相关信息。共享资产只需定义一次，后续章节直接引用其ID即可。

需明确标注有状态变化的变体：如满杯/空杯、关闭/打开的门、白天/夜晚光照效果、服装或表情变化等。道具变体未必对应新的网格模型；需说明是由材质、动画还是运行时状态决定了其表现形式。运行时行为应作为Mechanic任务处理，并与对应的所需资产关联。

## 4. 推导页面与界面状态针对每一章节，列出实际所需的入口界面、HUD、情境交互、对话、暂停/恢复及退出界面。为每个界面分配独立ID、布局模板ID、出入条件、内容槽位以及必需的绑定关系。对于仅内容不同的章节界面，应复用现有实现而非重复开发；标题页、设置页等共享外壳页面需与章节专属界面分开定义。相关设计可参考`agent_skills/game_design/interaction_design.md`以及`agent_skills/game_design/game_layout_templates/`中的品类模板。

## 5. 按依赖顺序安排工作

创建与章节绑定的任务链：剧情/设计 → 资源与机制合约 → UI绑定 → 组装 → 游玩验证。允许各模块并行独立开发，但UI绑定环节必须在机制合约最终确定后才能启动。任务记录与状态规则可参照`agent_skills/game_design/task_tracking.md`执行。

在拓展新功能前，需先完成当前章节的可玩循环验证。一旦剧情发生变更，需作废受影响的章节、资源、界面及下游任务引用。后续章节虽暂以大纲形式呈现，但需在粗略规划中明确其预期的资源与页面需求，绝不可遗漏。

## 6. 强制性逐项检查清单

需生成明确的需求、章节、资源、界面及任务清单。每行记录需包含`item_id`、`chapter_id`、`check`、`status`、`reference`和`issue`字段。状态可标记为`confirmed`（已确认）、`missing`（缺失）或`not_applicable`（不适用）；标记为`not_applicable`时需说明具体原因。需注意：设计确认与实现完成、游玩测试通过属于不同范畴，需单独记录。

- [ ] 将每项必需需求/剧情节点对应到具体章节及验收标准。
- [ ] 确认每章的时间窗口、剧情时间点、目标及剧情节点顺序。
- [ ] 确认所有分支跳转目标、出入条件及状态保留规则。
- [ ] 核查每章涉及的角色、场景、道具、动画、音频、VFX及UI资源。
- [ ] 确认每项资源的来源、复用情况、变体、依赖关系及验收标准。
- [ ] 定义白盒颜色图例：用统一的颜色搭配标签、符号或轮廓来区分主要功能/属性类别。
- [ ] 验证场景中及显示页面上各相关资源的语义颜色是否一致，且不存在所有权/状态提示冲突或隐藏信息泄露问题。
- [ ] 根据需求核查登录/入口界面、游戏内HUD、暂停、恢复及退出界面。
- [ ] 核查角色/单位档案及装备/配装查看界面：需支持全身或物体视角展示、合规的属性显示、插槽兼容性判断、对比功能、新内容发现提示以及模型缺失状态提示。
- [ ] 确认每个界面采用的品类模板、状态逻辑、绑定关系及视口可读性是否符合要求。
- [ ] 确认每项任务的输入、输出、依赖关系及验收凭证是否完备。
- [ ] 在标记某章节设计就绪前，需先解决下一章节的缺失项。

需针对每一项和每一章节扩展相关检查内容。未解决的ID需明确列出，严禁用“所有工作均已覆盖”这类笼统表述替代逐项确认。
