# 3AGameFactory游戏生成代理指南

当被要求使用3AGameFactory创建或优化游戏时，请先阅读本文档。它会引导你找到最基础的、针对特定任务的技能模块以及引擎API相关资料。本文档适用于**游戏资源生成工作**：包括生成美术资源、玩法逻辑、用户界面、场景。它并非源代码级别的API参考文档。

## 项目目标

3AGameFactory能够帮助AI agent将游戏需求转化为正确的游戏资源。它支持图像生成，T型姿势模型制作、3D物体建模、3D场景搭建、动画制作、音频处理、CG视频生成、玩法机制设计、用户界面开发，以及面向UE5、Blender、Unity、Godot 4全流程组装。

## 路径约定

本文档中出现的每个代码库路径，以及它所指向的各技能模块中的路径，均以代码库根目录为起点，表示为`<REPO_PATH>/...`。请将`<REPO_PATH>`替换为你本地克隆的`https://github.com/OpenDCAI/GameFactory-3A`仓库路径。

这一约定非常重要，因为技能模块与引擎参考代码**并不共享同一个父目录**：

| 写法 | 含义 |
|---|---|
| `<REPO_PATH>/agent_skills/engine_context/ue5_api.md` | 一个技能模块，位于技能树内 |
| `<REPO_PATH>/engine_adapters/ue5/` | 引擎参考代码——与`agent_skills/`同级，并非其内部子目录 |
| `<REPO_PATH>/pipeline/`、`<REPO_PATH>/operators/`、`<REPO_PATH>/models/`、`<REPO_PATH>/scripts/`、`<REPO_PATH>/test/`、`<REPO_PATH>/test_data/`、`<REPO_PATH>/third_party/` | 同样与`agent_skills/`同级 |


## 配置说明

配置应在游戏请求的最初阶段完成，即在任何资源处理工作开始之前进行。

**配置仅对应一个文件。** 所有的凭证信息、API基础地址、后端选择以及缓存位置均来自`<REPO_PATH>/.env`文件（模板为`.env.example`），该文件由`<REPO_PATH>/config.py`加载。每个云服务提供商都需要对应的`*_API_BASE`和`*_API_KEY`参数；流水线运行器在加载任何配置前会先调用`require_cloud_or_exit()`函数，因此一旦缺少相关参数，系统会在第一秒内报错，并提示需要添加的具体`.env`行内容。

切勿临时导出密钥，也不要想当然地认为存在默认端点。务必确认计划所需的服务提供商参数均已填写，同时确保相关开关已关闭本地默认设置：`AAAGF_3D_BACKEND`、`TPOSE_GEN_BACKEND`、`AAAGF_DIALOGUE_BACKEND`、`AAAGF_SOUND_EFFECT_BACKEND`、`GAMEFACTORY3A_VIDEO_BACKEND`。本地运行相关流程需要CUDA GPU以及数十GB的权重文件和磁盘空间；如果机器不满足这些条件，应选择云端方案（或采用已授权/下载的现有资源），而非强行启动本地流程。

## 端到端游戏生成工作流程针对每一项游戏开发请求，请务必遵循以下流程，在游戏方案确定前切勿直接着手代码编写或资源生成：

1. **明确需求概要**：确定目标引擎、游戏类型、玩家交互循环、目标平台、所需交付物、视觉风格、参考案例、预算以及验收标准。若用户未指定引擎或视觉风格，需在规划前询问；若仅缺少其中一项，需给出合理的默认选项并请用户确认后再继续实施。
2. **制定游戏规划**：查阅`<REPO_PATH>/agent_skills/game_design/SKILL.md`，将各项需求及脚本转化为故事线，梳理出按时间顺序排列的章节流程。需区分预估游玩时间与虚构剧情时间，明确各章节的目标、关键节点、分支路径以及进入/退出条件。据此确定每个章节的角色、环境、道具、动态效果、音频、视觉特效及前端界面，同时复用已有共享资源。在最终美术设计确定前，先审核采用基础颜色的JSON页面布局。要将下一个可玩章节拆解为依赖关系明确的任务，并在整个开发过程中维护与章节绑定的TODO记录。
3. **搭建可玩的白盒版本**：按照步骤2中确定的章节TODO列表及依赖关系推进开发。查阅`<REPO_PATH>/agent_skills/engine_context/engine_overview.md`，了解CodeGen工具及所选引擎的API规范。使用简单几何体与占位反馈元素，将场景、玩法、UI及章节切换功能整合为可运行的工作玩家循环。用统一的颜色及非色彩提示来区分主要功能或属性，保留稳定的资源ID以便后续替换。完成构建、启动并运行核心循环，解决阻碍问题，无需等待最终美术资源即可更新TODO记录。
4. **在白盒版本中优化资源**：查阅`<REPO_PATH>/agent_skills/asset_qa/README.md`，再参考对应资源类型的相关技能指南来完成资源的生成、获取及质量检查。根据白盒版本的反馈优先处理剩余的TODO任务。在预算、隐私限制及费用审批允许的范围内，优先选用成熟的云API来生成资源；若可靠性更高，则优先选用引擎自带的授权动效/场景库。替换占位资源前需通过结构与视觉层面的质量检查，同时保留原有的资源ID及玩法/UI接口规范。需在游戏中检查资源的缩放比例、朝向、附着关系、碰撞检测及动画效果，重新测试受影响的流程。要将资源的来源、授权信息及验证凭证记录在TODO中。
5. **对优化后的游戏进行验证、试玩与迭代**：资源集成后需重复执行构建、启动、试玩、记录及评审流程，发现问题后反复调整。此最终验证环节无法被之前的白盒检查取代，仅能成功编译也不足以说明开发达标。具体流程请参考下方的[验证、试玩与迭代](#validate-play-and-iterate)章节。

## 从任务要求开始

在编写或运行任何内容前，请先明确以下内容：1. **目标引擎** — `ue5`、`Blender`、`Unity3D` 或 `Godot`。
2. **所需交付物** — 资产、动画、音频、CG视频、游戏玩法、UI、场景，或是可完整游玩的游戏片段。
3. **验收标准** — 视觉风格、玩家交互方式、支持的平台、性能限制，以及判定成果合格所需的佐证材料。
4. **现有输入资料** — 需求文档、概念图、参考视频、已生成的产物，以及选定的引擎项目。

切勿混用不同引擎的API。除非需求明确要求多个独立交付物，否则请选定一个目标引擎。

## 资产决策策略

该策略适用于第4步中的生产资产或独立资产请求。第3步可使用简单的程序化占位符来验证游戏玩法，无需等待生产资产的就绪。需将这些占位符标记为待替换状态，而非已完成的资产。针对每个生产资产，需遵循以下流程：

1. **根据需求生成资产**。若有合适的云模型可用，优先选用；若出于需求、预算、隐私或离线执行的要求，则使用本地/开源模型。若需使用付费云后端，必须先获得用户授权：暂停当前操作，发送购买/API密钥页面，说明预估费用，获取密钥后再继续——详情参见`<REPO_PATH>/agent_skills/asset_qa/README.md`中的“付费云后端”章节。
2. **当生成质量不达标时，选用有授权的来源或备选方案**。需保留资产对应的源文件及许可/出处信息。严禁通过爬虫方式绕过需要登录或有使用限制的授权来源。
3. **若生成方式和允许的来源都无法提供可上线的资产，需上报缺口**。需说明缺失的功能、尝试的获取路径以及游戏的安全备选方案。

在宣称生成的或导入的3D内容可用于游戏之前，需先运行相关的视觉质量保证技能进行检测。即便网格结构有效，仍可能出现方向错误、缩放不合理或视觉效果不可用的问题。

## 验证、运行与迭代

第5步是资产优化后的完整验收环节。在第3步的白盒测试阶段以及第4步替换资产后，也需执行相应的可玩性检查；每个阶段都要记录相关证据。白盒测试证据并不能证明资产或呈现质量已达到最终标准。
“能够编译”、“能够启动”或“日志中无错误信息”**并不等同于验证通过**。1. **构建、启动并实际游玩。** 按照所选引擎的官方文档说明，使用其指定的客户端启动路径。不仅要测试游戏启动流程，还要执行**大部分玩家会进行的操作**：移动、跳跃/闪避、摄像机控制、攻击或射击、交互/拾取物品、载具驾驶、受伤与死亡处理、重生、胜负判定、暂停操作，以及所有承诺会实现的UI界面。至少要完整运行一次游戏核心流程，同时涵盖计划中提到的各种极端情况。

2. **录制游戏视频。** 通过浏览器服务端或引擎自带的录制功能捕捉上述操作过程——分辨率无需过高，时长也不用太长，只需作为验证依据而非宣传片即可。视频需覆盖闲置状态、角色移动、转向、主要动作、载具操作（如有）、特效触发、完整的UI展示以及场景切换等环节。一定要亲自观看录制的视频；绝不要仅凭源代码或一张截图就评判游戏质量。

3. **对照下表审核录制视频。** 表中的每一行都代表了编译过程和静态资源检查无法发现的故障模式。

4. **修复并迭代优化。** 将每个发现的问题记录为：视频中的具体现象 → 所属层级（资源、导入元数据、游戏机制、UI、场景、光照、特效）→ 修复方案 → 在新录制的视频中验证修复效果。务必在对应的层级内解决根源问题；绝不要把资源相关的问题硬塞进游戏代码里修补。反复执行“构建→游玩→录制→审核”的流程，直到满足验收标准且表中所有条目都通过验证为止。最终要保留或提交最终的审核视频、已测试的操作列表以及已修复的问题清单。如果存在未经验证的功能流程，应如实报告其能力缺口，而非草率宣称游戏已达标。| 审核区域 | 检查要点 |
|---|---|
| 图像质量 | 网格轮廓与拓扑结构瑕疵、纹理分辨率、材质表现、接缝问题、LOD切换异常。场景方面：构图合理性、地面/墙面连续性、孔洞、缺失的碰撞地板、绘制距离、雾效表现。 |
| 光照效果 | 曝光度是否合适、阴影是否过暗或缺失、光线是否从几何体缝隙泄漏、光照贴图/全局光照瑕疵、表面是否呈现全黑或过曝状态、角色与环境间的光照方向是否一致。 |
| 风格匹配度 | 调色板、对比度、后期处理效果及整体氛围必须与要求的风格相符（赛博朋克霓虹风、低多边形风格化、照片级写实风等）。即便画面干净，若风格不符也视为不合格。 |
| 动态特效 | 特效需在对应事件触发时正常播放并及时停止（无循环卡顿、单帧闪烁现象，角色死亡后特效也不会残留）；特效的规模、密度、强度需符合逻辑；特效需生成在正确的挂载点上并跟随物体移动；撞击、脚步声、引擎声及UI反馈需与动画、音效同步呈现。 |
| 移动时的朝向 | 角色移动时面部需朝向移动方向——不能出现向后行走或射击的情况；动画的前进轴向需与控制器及相机相对输入指令一致。武器枪口/刀刃需朝前且远离身体，投射物需沿该轴向发射。载具需向前行驶，转向方向正确，倒车时无前进动画。箭矢、导弹、无人机、坐骑的移动方向需与视觉上的前方一致。每次重新绑定骨骼、重新导入模型或调整轴向后都需重新检查，应在资产/导入元数据层面修复，而非通过游戏代码补偿旋转。 |
| 部件组合合理性 | 武器需握在把手处，**位于角色前方/身旁**，不能嵌入躯干或悬浮在手掌外，且需匹配正确的手部挂载点。载具车轮需位于底盘下方的四个轮拱内，接触地面，既不能陷入车身也不能悬空，需沿正确轴向旋转且前轮可转向。脚部需贴合地面，不能悬浮或陷入地面；桌上的道具、架子上的物品、墙面的挂件同理。头盔、背包、盾牌、炮塔需安装在对应的挂载点上并跟随骨骼运动。角色、武器、载具、门、房间的相对比例需符合逻辑。动画过程中不能出现物体穿插现象，不限于待机姿势。 |
| 可玩性 | 碰撞与物理机制正常（不会穿模掉入地面、不会卡住、无抖动现象）；摄像机不会穿透墙壁或角色，且能呈现可用的取景画面；操控响应灵敏且无轴向颠倒问题；UI清晰可读，在测试分辨率下定位准确，且与实际游戏状态绑定；不存在导致操作无法进行的卡顿现象。 |

## 完成规则- 必须严格遵守任务验收标准；不得为了便于运行而替换成其他游戏或引擎。
- 生成产物的路径需使用`<REPO_PATH>/pipeline/common/paths.py`来定义；切勿手动编写`<REPO_PATH>/test_data/outputs/`下的路径。
- 在通过相应验证前，生成的资源、游戏玩法、用户界面以及引擎集成内容需作为独立的交付物分别管理。
- 绝不能仅仅因为源代码已编写完成就宣称游戏可玩。构建、启动、代表性玩家操作测试以及视觉审查都是独立的验证依据。
- 针对游戏交付任务，需完成[验证、游玩与迭代](#validate-play-and-iterate)流程，留存或上报最终的低分辨率审查视频及对应的审核流程记录。在宣布游戏准备就绪前，需确认网格方向、变换参数、附着点、动画、碰撞检测、摄像机、操控逻辑、视觉特效、用户界面、光照效果以及风格是否符合要求。
- 凭证信息应存储在环境变量或本地密钥库中；绝不要提交API密钥、令牌或私有媒体文件。
