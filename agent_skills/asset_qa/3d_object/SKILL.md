# 生成的资产审核

审核3D模型的生成质量。

生成模型旨在优化与某张图像的相似度。但游戏还需要其他许多图像转3D指标无法衡量的要素，而这些要素在五个正交视图中都能看到。请在`Gen3DObjectOperator.run_art_plan`执行完毕后，立即在`result["preview_sheet"]`对应的图纸上运行此流程。

## 一、先选定生成路径

共有两条路径用于生成3D资产，**成本最低且够用的那条将被采用**：

| 路径 | 适用场景 | 成本 |
|---|---|---|
| **资产包调用**（`funcs/asset_pack.py`） | 物体是已解决的通用问题——箱子、标定靶、绑定人偶 | 数秒，一次下载，之后免费复用 |
| **AI大模型服务生成**（Tripo / Meshy） | 物体必须匹配某张概念图——人脸、生物、树木、布料 | 付费，耗时数分钟 |

选择依据只有一条：**这个资产需要匹配某个具体概念吗？**

不需要，就用资产包。这不是降级方案——对于货箱、校准模型这类物体，公开的CC0模型在质量上优于付费重新推导的结果，而且不花钱、不等待、还能在多次运行间保持一致。

需要，就走图像转3D。这是唯一能把参考图的形态特征带进网格的路径。

### 1.1 资产包调用

Khronos 的 glTF 示例库收录了模型社区已经解决的问题，全部为 CC0 授权，与引擎无关：`funcs/asset_pack.py` 下载所需文件并写入标准任务输出目录，**不接触任何引擎**。

```python
from operators.gen_3d_object.funcs import fetch_asset_pack, describe_pack

# 先看清包里有什么，以及哪些已经缓存
for entry in describe_pack():
    print(entry)

fetch_asset_pack(game_id="gameA_cyberpunk_shooter",
                asset_ids=("box", "xbot"))
```

产出与其它 `3d_object` 任务完全一致：一个 `.glb` 加一份 `meta.json`。`meta.json` 记录 `asset_id`、`asset_type`、三角形数、CC0 授权声明与上游地址，因此这份资产日后仍可追溯到它的出处。

| asset_id | 类型 | 三角形 | 用途 |
|---|---|---|---|
| `box` | prop | 12 | 最省事的连通性检查 |
| `box_textured` | prop | 12 | 需要 UV 时用 |
| `avocado` | prop | 686 | 有机曲面，能暴露平滑错误 |
| `lantern` | prop | 756 | 硬表面细节 + 金属玻璃材质 |
| `duck` | creature | 4,212 | 低模生物 |
| `damaged_helmet` | prop | 25,232 | PBR 硬表面主道具，法线贴图压力测试 |
| `xbot` | avatar | 3,896 | 已绑定骨骼的中性人偶 |
| `robot_expressive` | avatar | 23,358 | 含表情形变通道 |

下载缓存在 `test_data/outputs/_asset_pack_cache/` 下，因此重跑不产生网络请求，也不会发生漂移——通过一次检查的字节就是之后每次运行看到的字节。需要完全离线复现时传 `offline=True`，缓存未命中会直接报错而不是静默联网。

**资产包不会伪装成生成结果。** `meta.json` 里的 `source` 字段是 `asset_pack` 而非模型名，审核时看到它就应当知道：这个网格不是为本项目新做的，若概念与它不符就换资产或改走生成路径。

### 1.3 提示词是请求，不是约束

曾有三次请求要求生成没有车轮的汽车车身——"NO WHEELS"以三种不同方式表述，甚至作为主语出现——但生成的模型依然带了两组车轮和一组车拱，因为在该模型见过的所有场景里，汽车都配有车轮。

因此：请求生成*零部件*，而不是功能受限的完整物体。

每条路径生成完毕后，都可直接跳至*五项检查*部分。

## 二、环境准备

使用资产包仅需一次下载；AI生成路径则需要API密钥。

```bash
pip install -r requirements.txt
```

仅使用选定的路径。API密钥应存储在环境变量中。

**3D物体生成目前只有云端API可用——先选Tripo，再选Meshy**。这些服务是付费的，因此在首次调用前，**请暂停操作并参考`<REPO_PATH>/agent_skills/asset_qa/README.md`中的“付费云端后端”章节**：推荐合适的服务商，发送购买/获取API密钥的页面链接（<https://platform.tripo3d.ai/api-keys> 或 <https://www.meshy.ai/api>），说明包含重新生成尝试在内的、针对计划生成的网格数量的预估费用，请求用户购买访问权限并提供`TRIPO_API_KEY`/`MESHY_API_KEY`，待得到明确答复后再继续操作。

## 三、各引擎支持的文件格式

具体以各适配器的导入器为准，以下为实际可加载的格式：

| 引擎 | 支持的网格格式 |
|---|---|
| UE5 | `fbx`、`glb`、`gltf`、`obj`、`usd`、`usda`、`usdz` |
| Blender | `abc`、`fbx`、`glb`、`gltf`、`obj`、`ply`、`usd`、`usda`、`usdc`、`usdz` |
| Unity | `fbx`、`glb`、`gltf`、`obj` |
| Godot | `gltf`、`glb`、`fbx`、`obj`、`collada` |

**glTF是兼容性最好的格式，因此建议输出为`.glb`格式**。此处提到的所有流程均已默认采用该格式。建议选择`.glb`而非`.gltf`格式，因为单二进制文件不会存在`.bin`文件或纹理缺失的问题。

## 四、五项检查要点

**1. 是否符合要求？** 将生成的网格与同目录下的概念图（`concept.png`）以及设计文档中的描述进行对比。如果“宝箱”被重建为圆形块状物，这属于概念图设计问题，而非网格生成问题：应重新生成概念图，而非重新生成网格。

**2. 背面是否完整？** 单图像重建会凭空生成图像中未显示的部分。输入图像中未拍摄到的`-z`视角区域就是这类额外生成内容的所在。如果物体仅从正面被玩家看到（如建筑立面、墙面装饰物），背面平整、模糊或中空尚可接受；但如果是玩家能绕行查看的物体，背面不完整则不符合要求。

**3. 是否直立且完整？** 通过`+y`视角可以判断物体是否站立。如果概念图被裁剪，生成的网格也会相应截断——比如腿部分在脚踝处结束，树木没有树冠——这是因为几何形状在图像截止处就终止了。必须重新生成网格；后续流程无法修复此类问题。**4. 物体下方有地面吗？** 查看+y方向的视图，可看到物体周围有一层淡色区域；从侧面视图中则能看到其底部有一条细虚线。Image-to-3D会将输入图像裁剪为物体自身的轮廓，因此站立的人形模型会触及画面边缘，且模型常常会推断出存在地面平面——该地面平面的计算成本仅占三角形预算的五分之一；当模型按角色实际身高缩放后，会形成一块厚度为2.4米的灰色平板。

`<REPO_PATH>/operators/gen_3d_object`会自动移除这类地面（通过`funcs/mesh_cleanup.py`实现），并会反馈被移除的内容。审核表中标注的“实心板”意味着移除操作被拒绝；一旦移除操作的成本超过网格成本的40%，就会触发这一标注——在认定其为漏洞之前，请先查看该任务的`ground_plate`报告以了解原因。地面层面的稀疏斑点属于地面的碎屑，并无危害。

资产包中的网格也会跳过此项检查：它们来自人工制作的示例模型，移除操作可能会删掉本就存在的底座。

**5. 它符合预算要求吗？** 表格标题栏会注明三角形数量。相关预算参数存放在`<REPO_PATH>/operators/gen_3d_object/funcs/art_plan.py`中的`BUDGET_BY_ROLE`里，它是按角色而非资产类型分类的，因为决定预算的关键在于某类物体被渲染的频率：

| 角色 | 三角形数量 | 纹理分辨率 |
|---|---|---|
| `avatar`——主角，近距离可见 | 40,000 | 2048 |
| `weapon`——手持武器，屏幕上显示尺寸较小 | 20,000 | 1024 |
| `prop`——可交互物品，每个场景中出现1-2个 | 20,000 | 1024 |
| `scenery`——会重复出现数十次 | 8,000 | 1024 |
| `landmark`——仅远距离出现一次 | 20,000 | 1024 |

一棵三角形的数量达到200,000的重复树木，其成本甚至超过了场景中其余所有物体的总成本。请在规划条目中设置对应的`role`，然后**重新生成模型**：三角形预算无法事后调整，因为在生成器外部对带纹理的网格进行简化会导致UV坐标丢失，而生成器是在网格简化后才烘焙纹理的。切勿仅凭肉眼判断来随意简化已完成的资产。

**6. 尺寸比例合理吗？** 表格标题栏会注明生成的边界框尺寸。生成的网格会被归一化到单位立方体中，因此单独看这个数值并无意义——关键在于规划中设定的`height`是否符合该物体的实际高度。如果椅子的高度为3米、门洞高度仅为1.6米，这类比例失调的情况会让整个场景看起来像玩具。

## 五、记录最终结果
- **接受**：将朝向轴记录到任务输出中。若资产已被接受但朝向未经验证，则说明该资产尚未处理完成。
- **重新生成**：修改计划条目——包括提示词、种子值、`role`、`triangles`、`texture`等参数，并注明具体修改项，如此下次运行时会是全新的尝试而非重复之前的流程。
- **改用资产包**：如果某个资产其实并不需要匹配特定概念，换用资产包通常比反复重试更划算——它不花钱，且质量稳定。
- **拒绝**：换一个资产或路径。带着真实材质与适配阴影的资产包网格，往往比扭曲变形的生成结果更适合直接使用。

## 六、生成工具无法解决的问题

对于任何需要**动态交互**内容而言，生成工具同样并不适用。生成的网格是一个整体：汽车的轮子无法转动，箱子的盖子无法打开，角色也无法进行蒙皮处理。可行的做法是生成外壳，再把可活动部件交给引擎侧实现——这已经超出本流程的范围。
