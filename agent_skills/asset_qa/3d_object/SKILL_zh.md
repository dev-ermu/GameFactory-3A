# 生成的资产审核

根据与方向审核相同的渲染图纸，判断生成的网格是否适合在浏览器游戏中使用。

生成模型旨在优化与某张图像的相似度。但游戏还需要其他许多图像转3D指标无法衡量的要素，而这些要素在五个正交视图中都能看到。请在`Gen3DObjectOperator.run_art_plan`执行完毕后，立即在`result["preview_sheet"]`对应的图纸上运行此流程。

## 先选定生成路径

共有三条路径用于生成3D资产，成本最低的路径将被采用：

| 路径 | 适用场景 | 成本 |
|---|---|---|
| **规格化生成**（`funcs/code_asset.py`） | 物体可被精确描述——如箱子、标识牌、车轮、步枪、栏杆 | 仅需数秒，无需GPU，无需API密钥 |
| **资产包调用**（`funcs/asset_pack.py`） | 已有该物体的CC0授权模型可用 | 仅需数秒，一次下载即可 |
| **AI生成**（Tripo / Meshy / TRELLIS.2） | 物体以表面形态呈现——如人脸、生物、树木、布料 | 需付费或使用GPU，耗时数分钟 |

`suits_code_asset(subject)`会返回`code`、`generate`或`ambiguous`三种结果。它会直接拒绝模糊请求而非盲目猜测：若强行用程序化方式“描述”一张人脸，只会浪费迭代次数去尝试各种可能的调用方式，最终效果未必理想。

路径选择依据是**物体的组成方式**，而非其是否属于硬表面材质——步枪和盔甲都属于硬表面材质，但生成路径却不同：

| 拓扑类型 | 含义 | 对应路径 |
|---|---|---|
| `composed` | 各部件相邻排列、通过邻接关系拼接而成——如步枪、汽车 | `code` |
| `nested` | 各层附着于必须先存在且可被测量的载体之上——如穿在身上的盔甲 | 先`generate`生成载体，再定义各层（混合模式） |
| `surface` | 为不可分割的单一表面，无需组装——如人脸、树木 | `generate` |

结果还会包含`topology`、`claimed_by`和`builder`字段，这些正是混合构建流程的依据：`nested`类型的请求会指定负责将各层贴合到生成载体上的模块。

**对于结构固定的物体，优先选用规格化生成方式**——如赛车、手枪等零部件结构固定的物品。**人物类模型应直接通过AI生成**：手动拼接会导致迭代次数激增且效果更差——比如拼接一个骑士模型，就需要人类操作员花费12小时、经过8轮调整才能勉强达到可用程度——因此应直接将角色模型交由图像转3D工具处理。详情可查看`<REPO_PATH>/agent_skills/asset_qa/3d_object/composition_examples.md`。

**新增领域类别本质是注册一种生成策略，而非修改路由逻辑。** `funcs/code_asset_templates/`目录下的每个子包都定义了自身可生成的资产词汇表，因此拥有专属名词的项目应打包发布新子包，而非修改中央词表：

```python
from operators.gen_3d_object.funcs.code_asset_templates import routing

def claim(subject, asset_type="prop"):
    if "zorblatt" not in routing.words(subject):
        return None
    return routing.Claim(topology=routing.COMPOSED, strength=1.0,
                         evidence=("zorblatt",), reason="a stack of plates")

routing.register("zorblatt", claim)
```只需传入 `strategies=[(name, fn), ...]`，即可在不修改注册表的情况下，针对单次调用使用自定义的分类规则进行路由。

对于硬表面建模而言，规范并非一种降级处理——它明确了生成过程只能猜测的三件事：

- **朝向**（`forward`）：因此导入记录中会标记为 `verified_by="spec"`，而非 `heuristic`；
- **尺寸**（`height_metres`）：生成的网格会被归一化到一个单位立方体中，自身没有固定尺寸；
- **零部件**：每个零部件对应一个命名后的glTF节点，这样车轮仍能旋转。而生成的网格则是一个整体。

每条路由仍会经过审核——一旦网格生成完成，可直接跳至*五项检查*部分。

### 或者两者结合：组合生成的零部件

这些路由方式并不互斥。`mesh` 类型的零部件会从磁盘读取GLB文件——即云模型中的一个组件——随后会像基本几何体一样被定位、测量和约束。**这种划分并非凭个人喜好决定：**

| 生成方式 | 作为基本几何体的状态 |
|---|---|
| 某些形状无法通过公式描述——比如握把的凸起、汽车面板的褶皱 | 具有精确尺寸的物体——如轨道的槽距、桶的直径 |
| 表面本身即为资产 | 必须保持可分离性的物体，例如可转动的车轮 |

很容易犯的反向错误是：生成一个步枪瞄准镜竟耗费了**19,982个三角形**——这一数量相当于整个步枪基本几何体的三倍之多；而一个九点式`车削`操作就能精准描述这种呈阶梯状的软管形状。且不同于车削操作，这种方式无法通过调整参数来修正。

```python
{"id": "grip", "kind": "mesh",
 "source": "parts/grip.glb",       # 必填项，验证时须确保文件存在
 "size": [0.116, 0.116, 0.116],    # 统一尺寸：详见下文
 "at": [0, 0.045, -0.104], "rotation": [0, 90, 0],
 "long_axis": "y"}                 # 可选；需与顶点数据比对
```

**`size` 是一种请求，而非实际范围。** 网格会通过一个缩放因子来调整尺寸以保持比例——将成型的握把拉伸以填满指定盒子，其效果比实际尺寸略小4毫米的握把还要糟糕。若需刻意指定统一尺寸，需重复输入同一个数值；`provenance` 会对此发出警告，并报告用于定位相邻物体的 `actual_extent` 值。

**务必测量朝向，切勿想当然。** 获取的文件内并无信息说明其哪个轴对应长度方向。步枪握把的法兰部分沿*x*轴延伸，因此需要设置 `rotation: [0, 90, 0]`；若围绕*x*轴旋转——也就是直觉上认为的“向后倾斜”——反而会在其原本就平整的平面上造成倾斜。声明 `long_axis` 后，`orientation` 检查机制便会验证放置后的顶点朝向。**重新生成的零部件会有新的轴向**：同一握把重新获取时，所需的旋转角度从 `-90` 变成了 `+90`。

因此 `verified_by` 的值会变为 `spec+generated`——因为放置位置已被明确指定，内部的网格也符合规范。

`<REPO_PATH>/agent_skills/asset_qa/3d_object/composition_examples.md` 展示了以上三种示例的两种实现方式，可供并列参考。

### 纹理的处理

UV坐标和基础颜色图像会被整合到输出结果中，它们被封装起来并在不同放置场景中共享（比如四个车轮共用同一纹理源，或采用图集形式）。有两点需要注意：- **基础几何体不会生成UV坐标**，因为随意生成的UV会采样他人图集里的任意角落。
- **仅采用基础颜色属性**。当源模型包含金属度-粗糙度*贴图*时，其对应的参数会被替换为电介质材质的默认值，而非继承原有值：这些默认值被设为glTF格式的默认数值`1.0`，用于对该贴图进行缩放；因此如果不携带该贴图直接复制模型，就会把聚合物材质的握把渲染成喷砂处理的钢材效果。此类情况会被标记为`factors_from: "assumed"`。

**带纹理的部件成本较高，而`budget`参数明确规定了成本上限。** 首个带纹理的握把模型包含12,213个三角形，导致步枪模型总三角形数达到22,247个，超出了20,000个的预算上限——这一请求被拒绝是合理的。应降低`decimation_target`参数值重新生成模型；毕竟纹理细节已存储在图集中，无需使用一万两千多个三角形来呈现。

### 第三代生成器不会按请求执行的操作
提示词是一种请求，而非约束条件。曾有三次请求要求生成没有车轮的汽车车身——“NO WHEELS”这一要求以三种不同方式表述，甚至作为主语出现——但最终生成的模型却包含两组车轮和一组车拱结构，因为在该模型所见的所有场景中，汽车都配有车轮。

因此需据此规划：请求生成*零部件*而非功能受限的完整物体，并将所有需要单独分离或精确定位的元素放在几何体端处理。以汽车为例，车拱结构被纳入规格说明中，其与车轮共用相同的参数常量——位于`HALF_TRACK, WHEELBASE`位置的车拱不可能与同位置的车轮产生错位，这是生成的网格模型无法保证的特性。

**人物角色与其穿戴的盔甲是两个独立实体。** 当描述对象涉及穿戴者时（如“骑士”、“战士”、“女性”），若短语中包含表示穿戴的介词（如“骑士**身穿**板甲”）或该词作为主语（如“女骑士”），则归类为`nested`类型；而单独的盔甲部件仍归类为`code`类型，因为此时该词仅作为修饰语：“骑士头盔”本质上还是头盔。这种拆分属于混合路由逻辑——先生成身体模型，再声明护腿和剑的细节。

仅凭套装类词汇无法判定分类，试图如此判断正是最初的漏洞所在：“盔甲”和“板甲”也属于刚性组合类词汇，因此“身穿板甲的女骑士”这一描述会被判定为`code`类型，置信度高达0.9，原因是系统依据的是盔甲属性而非穿戴者本身。

## 根据规格说明生成模型
```python
op = Gen3DObjectOperator(model=None, run_id="20260826_1400")   # 无需指定模型
result = op.run({
    "game_id": "gameA_cyberpunk_shooter",
    "task_id": "crate_001",
    "asset_id": "supply_crate",
    "spec": {
        "subject": "木质补给箱",
        "units": "米",          # 必填项，无默认值
        "forward": "+z",        # 必填项，无默认值
        "asset_type": "道具",
        "height_metres": 0.6,
        "materials": {"wood": {"baseColor": [0.45, 0.30, 0.18, 1],
                               "roughness": 0.85}},
        "parts": [
            {"id": "body", "kind": "box",
             "size": [0.6, 0.6, 0.6], "at": [0, 0.3, 0], "material": "wood"},
        ],
    },
})
````units`和`forward`没有默认值，因为预设的朝向存在缺陷。`orientation_review.md`文档的存在就是为了规避这一问题：在资产被放入场景且向后移动之前，其朝向看起来都是正确的。

部件类型包括：`box`（立方体）、`cylinder`（圆柱体）、`cone`（圆锥体）、`sphere`（球体）、`torus`（圆环体）、`lathe`（车削体）、`extrude`（挤压体）、`mesh`（网格体）。其中，`lathe`会对一个`(半径, 高度)`轮廓进行旋转加工——比如制作瓶子、刀刃或车削腿型部件；`extrude`会将封闭的`(x, y)`轮廓沿Z轴拉伸；`mesh`则用于读取GLB格式文件（详见“两者皆可”章节）。任何部件都可以设置`parent`和`attach`属性（详见“关联关系”章节）。`segments`参数用于控制圆形部件的三角面数量，`chamfer`（取值范围0–0.5，为半边长的一部分）可用于对立方体的边缘进行倒角处理——尖锐的边缘会反射光线形成一条硬朗的线条，这正是立方体看起来像玩具积木的原因。

### 关联关系而非坐标

有两个字段能将部件列表转化为结构化对象，且这两个字段会在任何处理逻辑运行前就被解析：

| 字段 | 含义 | 用途 |
|---|---|---|
| `parent` | 该部件是另一个部件的子部件 | 比如肢体上的护甲、轴上的车轮 |
| `attach` | 将一个部件的某一面贴合到另一个部件上 | 任何需要放置在另一物体上、悬挂于其下方或与其相接的部件 |

```python
{"id": "vambrace-l", "kind": "cylinder", "size": [0.105, 0.16, 0.105],
 "parent": "forearm-l", "at": [0, 0.01, 0]}          # 相对于前臂的坐标

{"id": "muzzle", "kind": "lathe", "profile": [...],
 "attach": {"to": "barrel", "axis": "z", "gap": 0.0}}  # 已解析，无需手动测量
```

之所以需要`attach`机制，是因为绝对坐标定位很容易失效。此处所有资产中的间隙问题都源于此：枪口与枪管之间相差9毫米，护胫与小腿之间相差16毫米，吊索环与导轨之间相差26毫米——这些问题都是通过`connectivity`功能发现的，经人工测量后确定数值，但一旦相邻部件位置改变，这些数值就会失效。`attach`还能处理目标部件发生旋转的情况，因为旋转后部件的占用范围并不再由其`size`参数决定。

面的位置分为`min`/`mid`/`max`，默认设置为相对面（`my: "min"`，`their: "max"`——即一个部件放置在另一个部件顶部）。`gap`参数用于设定两个部件之间的间距，`offset`则用于沿另外两个轴向调整位置。

`parent`属性会使部件成为glTF节点的子节点，因此这种层级关系在导出时得以保留：比如引擎旋转`forearm-l`时，也会带动护腕一起转动。如果没有`parent`属性，命名后的部件虽可被引用但无法相互关联，要为角色设置姿势时就需重新计算每个部件的位置。声明顺序并不重要——解析器会遍历依赖图，并通过名称检测来避免循环引用。

### 从模板组合而非编写脚本

`funcs/code_asset_templates/`目录下存放着人物、套件及连接机制的模板，这些是供操作员阅读的**输入内容**，而非自动执行的排列规则。这些模板按拓扑结构分类：

| 路径 | 内容 |
|---|---|
| `routing.py` | 注册表与`Claim`类——属于底层机制，不涉及具体词汇 |
| `compose.py` | 将部件与材质组合成规格说明——所有流程都会用到 |
| `assembly.py` | 通过`attach`实现部件连接：包括`chain`、`group`、`mirrored`等模式 |
| `rigid_template/` | 刚体拼接模板：声明`composed`，拥有独立的词汇体系 |
| `human_template/` | 人物模型及其穿戴物：声明`nested` |
| `surface.py` | 声明`surface`；仅为一种策略，并不实际生成任何内容 |对于模型而言，组合指的是“身体”加上“所穿戴的装备”，且顺序必须如此——因为穿戴在肢体上的盔甲必须随肢体一同运动：

```python
from operators.gen_3d_object.funcs.code_asset_templates import compose
from operators.gen_3d_object.funcs.code_asset_templates.human_template import (
    humanoid, plate_armour)

spec = compose.compose(
    subject="女性骑士",
    body=humanoid.body_parts(),                   # 嵌套的肢体结构
    worn=plate_armour.plate_armour()              # 每件盔甲部件都依附于对应肢体
         + plate_armour.sword(),
    height_metres=humanoid.LANDMARKS["height"],
)
```

对于已组合的模型，只需声明其组成部分，交由`assembly`函数将它们拼接起来即可——即便相邻部件的尺寸发生变化，已确定的关联关系也不会失效：

```python
from operators.gen_3d_object.funcs.code_asset_templates import assembly

parts = assembly.chain([receiver, barrel, muzzle])          # 从前到后排列
parts += assembly.group(wheels, to="chassis")               # 轮组属于底盘的一部分，并非线性链状结构
parts += assembly.mirrored([skid], axis="x")                # 两侧对称部件，仅需定义一次
```

`chain`函数会跳过那些本身已带有`attach`或`parent`属性的部件，因此只需单独声明分支结构，其余部分按链式排列即可。每个链接的覆盖参数可放在`link`字典中（包含`axis`、`gap`、`my`、`their`、`offset`等字段），这些参数会在验证前被剔除。

**Spec与混合路由的区别仅在于一个参数**，这一差异恰恰验证了组合操作是否真的属于数据驱动范畴：

```python
    replace={"head": {"kind": "mesh", "source": "parts/head.glb",
                      "size": [0.27] * 3, "long_axis": "y"}},
```

`replace`采用合并而非覆盖的方式处理，因此新生成的头部会保留使其成为头部的附着关系。`drop`则用于删除特定部件。在解析器运行前，系统会**按名称校验**并拒绝删除某部件上所穿戴的装备——如果在图遍历过程中发现悬空的父级节点，所报错的名称往往并不准确。

请将这些内容作为模板编写成新的模型，而非作为`test_data`下的脚本。构建脚本会决定使用哪些部件以及材质的具体含义；解剖结构与装备配置应定义在模板中，这样后续建模时只需进行简单配置即可。像步枪的弹膛、汽车的轴距这类部件“表”——即具体的内容描述——会随对应的构建流程一同保存。

**车削轮廓的起点和终点半径必须为0**。否则旋转生成的曲面会变成两端开口的管道：既没有内部空间，当物体位于其后时还会形成可穿透的孔洞。这类情况会在验证阶段被直接驳回，因为与比例设定不同，这种情况根本不存在合理的设计意图。轮廓可沿任意方向绘制——系统会通过有符号面积来标准化处理，因此无需额外记忆缠绕规则。

### 门控逻辑：先于任何渲染器执行

系统会对Spec自身的几何结构进行八项检查，以便直接在顶点层面发现缺陷，而非等到渲染之后。所有检查结果会一并返回，因此只需一次遍历就能获取完整列表。| 检测项 | 检测对象 | 是否阻断？ |
|---|---|---|
| `solidity` | 厚度不足以使其在侧视时消失的部件 | 是 |
| `chirality` | 属于旋转关系而非镜像关系的`-l`/`-r`配对 | 是 |
| `scale` | 与`height_metres`参数不符，或小数点位置错误的部件 | 是 |
| `budget` | 超出该角色允许数量的三角面 | 是 |
| `connectivity` | 未与其他任何部件接触的部件 | 否——仅记录报告 |
| `provenance` | 被委托给生成器处理的内容及其生成成本 | 仅当该资源确实是生成的资产时才检测 |
| `orientation` | 读取的部件其长轴方向与声明位置不符 | 否——仅记录报告 |
| `windings` | 内外翻转或未闭合的部件；对于基础几何体直接阻断，对于读取的网格仅记录报告 |

**最需要理解的是`chirality`检测项**，因为其判定失败时的表现看似正常。对两个轴取反相当于180度旋转，而旋转会保持物体的手性——最终得到的两半物体手性是一致的。以[img2threejs](https://github.com/img2threejs/img2threejs)中的测量结果为例：z轴从`+0.288`变为`-0.288`，而镜像操作不会改变z轴数值。**仅需对横向轴取反即可**。任何左右对称的部件——如车头灯、后视镜、吊臂转轴——都属于此类符号错误。

`windings`是唯一会评估网格的检测项，它存在的原因是曾有四种基础几何体以内外翻转的状态通过其他所有检测：GLB文件有效、计数匹配、边界范围正确，且不剔除背面的查看器对翻转后的实体渲染效果并无差异。这类问题通常会在引擎中首次显现。出于同样的原因，检查网格时需开启背面剔除功能。

`connectivity`仅负责记录报告：悬浮的晶体属于设计需求，若该项检测失败，则会导致该类资源无法通过检测。`provenance`也主要承担记录报告功能——仅当资源组成中大部分为生成的部件和三角面时才会检测失败；此时该资源属于附加了基础几何体的生成类资产，应经过`orientation`检测，而非直接沿用原有规格标签。未闭合的读取网格同样会被记录但不会判定为失败：修改规格无法修复此类问题，而阻断无人能修复的问题会导致流程中断，因此这类检测项会被绕过。

检测失败的項目不会写入任何内容，也不会向引擎传递任何信息——已存在的资源仍会被正常使用。仅当需要检查有问题的网格时，才需设置`strict=False`。

### 修正规格
调用`revise(spec, failures) -> spec`可让模型自行修复缺陷。循环最多执行三次，若出现`repeating`、`oscillating`、`no_progress`或`revise_failed`情况则会提前终止；`result["stop_reason"]`会说明终止原因。在[img2threejs](https://github.com/img2threejs/img2threejs)中曾出现过无限循环，导致记录一辆完全不动的汽车耗时45分钟，原因是查找操作返回了`None`，而循环仍在优化无法识别该结果的指标。

重新运行前请先查看`stop_reason`。若为`repeating`，说明本次修订未解决任何问题，此时第四次尝试实则等同于第三次尝试。

## 环境搭建
规格无需任何特定环境——仅依赖标准库，无需GPU、无需密钥。只需搭建你实际选择的生成路径即可。```bash
# Tripo和Meshy等云端3D后端
bash scripts/asset_env_setup/3D_object/cloud_api_install.sh

# 可选的本地TRELLIS.2运行环境
bash scripts/asset_env_setup/3D_object/trellis2_install.sh
```

仅使用选定的路径。API密钥应存储在环境变量中，大型本地检查点则应放在源代码控制之外，或存放于`<REPO_PATH>/third_party/`目录下。

**优先选择云端API——先选Tripo，再选Meshy**——相比本地TRELLIS.2，它们能生成更适合游戏使用的网格模型，且可靠性更高。不过这些服务是付费的，因此在首次调用前，**请暂停操作并参考`<REPO_PATH>/agent_skills/asset_qa/README.md`中的“付费云端后端”章节**：推荐合适的服务商，发送购买/获取API密钥的页面链接（<https://platform.tripo3d.ai/api-keys> 或 <https://www.meshy.ai/api>），说明包含重新生成尝试在内的、针对计划生成的网格数量的预估费用，请求用户购买访问权限并提供`TRIPO_API_KEY`/`MESHY_API_KEY`，待得到明确答复后再继续操作。只有当用户拒绝或需要离线执行时，才使用本地TRELLIS.2。

## 各引擎支持的格式

具体以各适配器的导入器为准，以下为实际可加载的格式：

| 引擎 | 支持的网格格式 |
|---|---|
| UE5 | `fbx`、`glb`、`gltf`、`obj`、`usd`、`usda`、`usdz` |
| Blender | `abc`、`fbx`、`glb`、`gltf`、`obj`、`ply`、`usd`、`usda`、`usdc`、`usdz` |
| Unity | `fbx`、`glb`、`gltf`、`obj` |
| three.js | `glb`、`gltf` |

**glTF是兼容性最好的格式，因此建议输出为`.glb`格式**。此处提到的所有流程均已默认采用该格式。需要注意的一点是：three.js仅支持glTF格式，因此从云端后端获取的FBX文件在用于浏览器游戏前需要转换格式，而同一文件直接导入UE5或Unity时则无需额外处理。

建议选择`.glb`而非`.gltf`格式——单二进制文件不会存在`.bin`文件或纹理缺失的问题。

## 五项检查要点

**1. 是否符合要求？** 将生成的网格与同目录下的概念图（`concept.png`）以及设计文档中的描述进行对比。如果“宝箱”被重建为圆形块状物，这属于概念图设计问题，而非网格生成问题：应重新生成概念图，而非重新生成网格。

**2. 背面是否完整？** 单图像重建会凭空生成图像中未显示的部分。输入图像中未拍摄到的`-z`视角区域就是这类额外生成内容的所在。如果物体仅从正面被玩家看到（如建筑立面、墙面装饰物），背面平整、模糊或中空尚可接受；但如果是玩家能绕行查看的物体，背面不完整则不符合要求。

**3. 是否直立且完整？** 通过`+y`视角可以判断物体是否站立。如果概念图被裁剪，生成的网格也会相应截断——比如腿部分在脚踝处结束，树木没有树冠——这是因为几何形状在图像截止处就终止了。必须重新生成网格；后续流程无法修复此类问题。**4. 物体下方有地面吗？** 查看+y方向的视图，可看到物体周围有一层淡色区域；从侧面视图中则能看到其底部有一条细虚线。Image-to-3D会将输入图像裁剪为物体自身的轮廓，因此站立的人形模型会触及画面边缘，且模型常常会推断出存在地面平面——该地面平面的计算成本仅占三角形预算的五分之一；当模型按角色实际身高缩放后，会形成一块厚度为2.4米的灰色平板。

`<REPO_PATH>/operators/gen_3d_object`会自动移除这类地面（通过`funcs/mesh_cleanup.py`实现），并会反馈被移除的内容。审核表中标注的“实心板”意味着移除操作被拒绝；一旦移除操作的成本超过网格成本的40%，就会触发这一标注——在认定其为漏洞之前，请先查看该任务的`ground_plate`报告以了解原因。地面层面的稀疏斑点属于地面的碎屑，并无危害。

根据规格制作的资产会跳过此项检查：规格无法凭空设定地面，对这类资产执行移除操作可能会删除原本要求添加的底座。

**5. 它符合预算要求吗？** 表格标题栏会注明三角形数量。相关预算参数存放在`<REPO_PATH>/operators/gen_3d_object/funcs/art_plan.py`中的`BUDGET_BY_ROLE`里，它是按角色而非资产类型分类的，因为决定预算的关键在于某类物体被渲染的频率：

| 角色 | 三角形数量 | 纹理分辨率 |
|---|---|---|
| `avatar`——主角，近距离可见 | 40,000 | 2048 |
| `weapon`——手持武器，屏幕上显示尺寸较小 | 20,000 | 1024 |
| `prop`——可交互物品，每个场景中出现1-2个 | 20,000 | 1024 |
| `scenery`——会重复出现数十次 | 8,000 | 1024 |
| `landmark`——仅远距离出现一次 | 20,000 | 1024 |

一棵三角形的数量达到200,000的重复树木，其成本甚至超过了场景中其余所有物体的总成本。请在规划条目中设置对应的`role`，然后**重新生成模型**：三角形预算无法事后调整，因为在生成器外部对带纹理的网格进行简化会导致UV坐标丢失，而TRELLIS.2是在网格简化后才烘焙纹理的。切勿仅凭肉眼判断来随意简化已完成的资产。

**6. 尺寸比例合理吗？** 表格标题栏会注明生成的边界框尺寸。生成的网格会被归一化到单位立方体中，因此单独看这个数值并无意义——关键在于规划中设定的`height`是否符合该物体的实际高度。如果椅子的高度为3米、门洞高度仅为1.6米，这类比例失调的情况会让整个场景看起来像玩具。

## 记录最终结果- **接受**：执行方向性检查（`<REPO_PATH>/agent_skills/asset_qa/3d_object/orientation_review.md`），并记录其朝向轴。若资产已被接受但朝向未经验证，则说明该资产尚未处理完成。按规范生成的资产会将朝向信息作为数据内置，因此检查环节只是确认而非重新设定朝向。
- **重新生成**：修改计划条目——包括提示词、种子值、`role`、`triangles`、`texture`等参数，并注明具体修改项，如此下次运行时会是全新的尝试而非重复之前的流程。
- **切换方案**：如果生成的网格在规格明确要求的某方面（如缩放比例、朝向、可活动部件）连续两次出现错误，就说明该物体其实是可以被清晰描述的。此时应编写对应的规格说明，而非盲目进行第三次生成尝试。
- **拒绝**：保留原始的基础几何体作为备选。这才是切实可行的解决方案。带有真实材质且阴影适配的倒角基础几何体，远比扭曲变形的网格效果更好；而且无需修改代码，`assets.instantiateOrBuild`就会自动调用这种备选方案。

## 生成工具无法解决的问题

在动用GPU之前，应先考虑使用框架。按每行代码带来的视觉效果强弱排序，生成的three.js场景效果由`host.setEnvironment({ preset })`、电影级色调映射、适配的阴影相机、倒角边缘、真实材质以及接触阴影共同决定——相关内容均记录在`<REPO_PATH>/agent_skills/engine_context/three_js_api.md`中。充满生成模型的无光照场景依然看起来像无光照场景；而由基础几何体构成的带光照场景则不然。

对于任何需要**动态交互**的内容而言，生成工具同样并不适用。生成的网格是一个整体：汽车的轮子无法转动，箱子的盖子无法打开，角色也无法进行蒙皮处理。要么生成外壳，再将可活动部件作为由游戏逻辑驱动的基础几何体——这正是`entity.visual`的作用；要么完全按照规格说明来构建，此时每个部件都已是命名好的节点。
