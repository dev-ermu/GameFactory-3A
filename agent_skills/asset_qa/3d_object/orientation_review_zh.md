# 导入资产朝向核查

确定导入的3D模型的朝向，并记录结果。

之所以需要这项技能，是因为该信息无法被自动计算出来。glTF文件会固定轴向和单位，但不会对模型朝向做出强制性规定，因此一个面向+Z轴建模的角色和面向-Z轴建模的同一角色，其边界框、节点树和动画片段在字节层面是完全相同的。加载文件时无法区分二者，但肉眼观察可以分辨——这就是为什么视觉识别模型是合适的工具，而启发式算法并不适用。

一旦知晓问题所在，成品游戏中的表现就一目了然；在此之前则难以察觉：玩家奔跑时角色却横向移动；敌人向后冲锋；汽车车头朝后行驶；宝箱向远离玩家的方向打开。这些情况下既不会报错，也没有测试失败，但游戏逻辑就是错误的。

精选的CC0资源包中的所有三个模型都面向**+Z轴**。运行时系统会将**-Z轴**判定为前进方向。因此，在这项核查之前生成的所有游戏，其角色都会向后移动。

## 执行时机

在任何网格导入之后、宣布游戏开发完成之前执行此流程：
- 在调用`three.assets.import_asset`、`import_avatar`、`import_prop`或`import_weapon`之后，或者在`run_art_plan`或`fetch_asset_pack`完成内容导入之后；
- 每当`assets.import_asset`返回关于未声明的`forward_axis`的警告时；
- 每当某个资源的`orientation.needs_vision_check`属性值为`true`时；
- 每当审核人员反馈角色存在“横向移动”“向后行走”“朝向错误”或“背对摄像机”等问题时。

纹理、材质、音频和动画片段无需进行此项核查：它们没有正面概念。如果资源清单中没有`orientation`区块，就属于此类情况。

## 判定依据与输入信息

决策前请先阅读以下内容：
- `three.preview.orientation_report`返回的渲染视图和几何证据；
- 资源自身的元数据（`three.assets.get_orientation`）；
- `<REPO_PATH>/agent_skills/engine_context/three_js_api.md`文档中*资产朝向*和*预览*相关章节的内容。

渲染视图的优先级高于一切。几何特征可以缩小答案范围，但无法最终确定答案；如果证据和图像结论不一致，以图像为准。

## 工作流程

1. **渲染。** 对每个已导入的网格资源执行以下操作：
   ```python
   report = three.preview.orientation_report("<asset_id>")
   sheet  = report["payload"]["contact_sheet"]
   ```
   生成的sheet是一张带有标签的合并图像，包含五个正交视图。单个视图文件存储在`report["payload"]["views"]`路径下。

2. **读取标签而非布局。** 每个视图都标有说明：`camera on<axis> | screen right = <axis>`。名为`+z`的视图是由位于+Z轴上、朝向原点拍摄的摄像机生成的，因此该视图显示的是模型的**+Z面**。特意没有将任何视图命名为“正面”：命名会预先假定答案。

3. **确定朝向。** 按照可靠性从高到低的顺序，利用以下线索找出模型正对摄像机的那个视图。| 主体 | 朝向面为以下部分 |
|---|---|
| 人形角色 | 眼睛、鼻子、嘴巴、胸部、皮带扣、脚尖 |
| 四足动物 | 口鼻部和耳朵（尾巴位于相反一侧） |
| 载具 | 引擎盖、格栅、前大灯、挡风玻璃斜面 |
| 枪械 | 枪口——沿枪管方向，这是唯一“前方”并非面部所在的情况 |
| 建筑、拱门、门口 | 玩家可通行的开口处 |
| 箱子、柜子、冰箱 | 盖子铰链位于后方；锁扣位于前方 |

模型的`forward_axis`即为该视角标签中所命名的轴向。

4. **通过第二个视角进行合理性校验。**在`-x`视角中，屏幕右侧对应`+z`轴。因此，朝向`+z`轴的模型在`-x`视角中应显示在右侧，在`+x`视角中则显示在左侧。若不符合这一规律，则说明步骤3中的判断有误。

5. **检查垂直轴。**在`+y`（俯视）视角中，站立的人形角色应呈现为紧凑的小型轮廓。若俯视图中能看到该主体的全长，则说明模型处于平躺状态：其坐标系为Z轴向上。在调整偏航角之前，需先记录`pitch_offset_degrees`值为`-90`或`90`——取能使模型直立的数值——因为俯仰角会改变水平轴向。

6. **读取缩放比例。**表格标题中标注了模型单位的包围盒尺寸。将其高度与主体的实际高度对比：身高4.46单位并不等于4.46米；这其实是一个按其他单位制作的、身高1.8米的角色模型。

7. **记录最终判定结果。**只需调用一次接口，这就是本次校验的核心目的：

```python
three.assets.set_orientation(
    "<asset_id>",
    forward_axis="+z",          # 步骤3得出的结果
    scale_hint_metres=1.8,      # 步骤6得出的结果
    verified_by="agent_vision", # 切勿省略此项
    notes="眼睛和面罩位于+Z侧。",
)
```

适配器会根据此信息计算偏航角，将其写入`public/assets/manifest.json`，运行时会在实例化时应用该角度。游戏逻辑代码无需任何修改。

8. **验证结果。**重新读取`three.assets.get_orientation("<asset_id>")`，确认`runtime_yaw_degrees`与步骤3的推断一致：`+z → 180`，`-z → 0`，`+x → 90`，`-x → 270`。

## 判断图像是否模糊不清

若无法明确判定，直接说明即可，切勿猜测。记录下的错误猜测比不记录更糟糕，因为这会阻碍后续校验工作继续开展。- **无正面特征的对称物体**（如板条箱、木桶、岩石）：无需记录其朝向，并说明原因：这类物体不存在容易搞错的“正面”。
- **纹理中绘制的面部无法解码**：当无法读取基础颜色纹理时，系统会发出警告。此时可根据轮廓判断物体类型：鞋头、鼻子、背包、尾巴、头发等。
- **模型朝向为对角线方向**：不符合任何主轴方向。此时应记录从最近主轴算起的`yaw_offset_degrees`值，而非使用`forward_axis`，同时需注明该数值是估算得出的。
- **完全无法识别的模型视图**：应标记为需要重新生成，而非直接标注信息。一个从五个角度都无法辨认的网格模型，在游戏运行时也照样无法被正确识别。

## 切勿这样做
- **不要在游戏代码里旋转模型**。实体中设置的`rotation.y += Math.PI`对使用该模型的其他模块而言是不可见的——无论是世界设定、后续游戏版本，还是原本基于特定朝向设计的动画——而且一旦该实体自行设置朝向，这种旋转就会被悄悄覆盖。正确的做法是统一在一个地方记录这一事实，供所有使用者参考。
- **不要手动编辑清单文件**。每次导入模型时，清单文件都会被重写。
- **不要为了修正旋转问题而重新导出或生成网格**。修改一个数字只需几秒的GPU运算时间，远比重新生成整个网格高效得多。
- **未经查看图像就不要设置`verified_by="agent_vision"`**。这个标记是唯一能证明有人已经核查过模型的信息。
- **不要根据动画剪辑名称推断物体朝向**。名为`Walking`的剪辑会沿着创作者选定的任意轴移动，而这个轴同样是未知的。

## 实操示例
`RobotExpressive.glb`模型在三款游戏中被用作虚拟角色：
- `+z`视角下可见两只眼睛和面罩；`-z`视角下可见光滑的圆顶背部；`-x`视角下眼睛位于屏幕右侧，而屏幕右侧恰好对应`+z`方向——各视角表现一致。
- `+y`视角下模型呈圆盘状：说明模型是直立状态，`+Y`轴为竖直方向，无需进行俯仰校正。
- 文档标题显示“边界框尺寸为2.63×4.46×2.69单位”；由于该物体是人形机器人，对应身高约为1.8米。
- 最终判定结果：
  ```python
  three.assets.set_orientation(
      "robot_expressive",
      forward_axis="+z", scale_hint_metres=1.8,
      verified_by="agent_vision",
      notes="眼睛和面罩位于+Z侧；模型原高为4.46单位。",
  )
  ```
- 调用`get_orientation`后，会返回`runtime_yaw_degrees: 180`，此时机器人即可向前行走。

## 成本说明
渲染器仅依赖`numpy`和`Pillow`库：无需GPU、无需显示器、无需浏览器，也无需Node进程。处理一个模型仅需约两秒就能完成五个视角的分析，因此审核整款游戏的艺术资源包所花费的时间，甚至比导入模型的时间还要短。
