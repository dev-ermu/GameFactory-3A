# 生成3D场景——策略技巧

选择构建`3D_scene`资源的方式。切勿为所有任务都采用同一套流程：用户指定的场景外观比场景类型更重要，而生成式重建在此处是最不稳定的方案。

## 决策原则

首先询问：**用户是否指定了场景的3D外观？**

| 情况 | 优先选择 | 原因 |
|---|---|---|
| **未指定外观**——没有参考图像，也没有描述性的外观要求 | **可下载、已校验许可的资源**。在所选引擎自带的资产库中搜索可用的场景或环境套件：UE5（Fab/Marketplace、Quixel）、Unity（Asset Store、相关包）、Godot（资产库）、Blender（内置资产、CC0授权资源库）、three.js（精选的CC0授权资源包——详见`<REPO_PATH>/agent_skills/engine_context/three_js_api.md`） | 由于外观没有限制，经过许可、由专业艺术家制作的场景比任何生成的内容都更适合交付使用，且能通过既定路径导入。需记录资源的来源与许可信息。 |
| **指定了外观**——有参考图像或明确的外观描述 | **先铺设地形/地面，再添加前景物体**（详见下方的“先铺地面，再放物体”说明，以及用于自动化操作的“场景构建代码链”） | WorldPlay风格的重建方案目前还不足以作为默认选择。先铺地面再加装饰物这种方式可控性强、可编辑，能可靠地还原用户要求的外观。 |
| **指定了外观，且空间为室内/封闭空间，同时用户需要高保真效果** | WorldPlay风格重建方案 | 这是唯一一种可以容忍该重建方案不稳定性的场景：封闭空间没有地平线或天空作为参照，一张参考图像就能完整呈现整个室内布局。 |

即便用户指定了外观，如果现有库中的场景已经符合要求，也优先选择可下载的资产——生成本身并非最终目标。

切勿悄悄更换策略。需说明你选择了哪一行规则及原因；如果用户在非室内高保真场景下要求采用重建方案，需先告知用户这是不稳定的方案，再投入时间处理。

### 若用户对场景一致性不满意

基于重建生成的场景常常会出现一致性问题：帧与帧之间几何形状偏移、遮挡边界处深度拉伸、天空或背景被拉成幕布状、出现孔洞和不连续的表面，以及场景不同区域的外观存在差异。这是当前“先生成再重建”流程的已知局限性，并非配置错误。

当用户提出此类问题时，**简要说明原因并提供解决方案**——不要反复重新生成：

1. 用一两句话说明问题所在：场景几何重建存在不一致现象，该问题源于视频/深度重建过程，而非参数设置不当；
2. 建议切换为“以地面为基准的构图方式”，或直接采用可下载的素材库场景，这样能确保视觉效果是人为设计的，而非凭空推断得出的；
3. 如果重建结果中还有可用的部分，仅保留这些部分作为布局参考。

## 场景类型仍决定几何策略

选定路径后，需对空间进行分类。若任务说明中未明确提及，则根据参考图像和需求文本判断：存在可见的围合墙面且空间有界→属于封闭场景；地面延伸至地平线或天空开阔→属于开放场景。

| 场景类型 | 几何策略 | 原因 |
|---|---|---|
| 封闭/室内/有界场景（房间、走廊、有墙的竞技场） | 当画质要求较高时，采用WorldPlay风格的重建方式 | 一张参考图像可转化为多视角视频，进而生成连贯的场景网格 |
| 开放/室外/无界场景（田野、道路、街区、地形） | 使用基准平面或地形，再放置物体 | 地平线和天空会干扰深度到网格的转换；以地面为基础搭配道具的构图方式更易于控制 |

## 封闭场景——采用WorldPlay/点云转网格方案

当可游玩空间为封闭结构、需要高画质效果，且大部分几何信息需源自单一视觉参考时使用该方案。

本代码库中典型的处理流程如下：
1. 参考图像（可选搭配提示词/相机位姿）→ 生成WorldPlay视频帧
2. 视频帧→ 生成WorldMirror深度图/点云
3. 点云→ 转换为连续网格（`<REPO_PATH>/operators/gen_3d_scene`，会剔除天空部分并生成切平面面片）
4. 将生成的GLB/PLY格式文件导出到`3d_scene`输出路径下

适用场景：
- 室内房间、洞穴、隧道、有明确墙面/天花板的小型竞技场，且对画质要求高——这是唯一推荐默认采用该方案的情况
- 参考图像已清晰呈现玩家将身处其中的布局
- 需要单个融合的场景网格，而非单独制作的道具

注意事项：
- 稳定性：该流程是本工具中最不可靠的方案，可能会出现场景内元素不一致的情况，需做好切换为“以地面为基准的构图方式”或素材库场景的准备
- 遮挡边界以及天空/背景部分仍需通过`gen_3d_scene`中的网格处理机制来优化（如天空分割、切平面连续性处理、法线一致性筛选）
- 不要指望通过该方案生成完美的无限室外地平线效果

入口文件：`<REPO_PATH>/pipeline/assets_gen/gen_3d_scene/{run,eval,render}.py`、`<REPO_PATH>/tests/test_3D_scene_gen.py`。

## 先确定地面，再放置物体——基准平面/地形+物体方案

当用户指定了特定视觉效果时，这是默认采用的方案；对于任何大面积、以地面为基础构建或可复用资产的世界而言，这也是正确的方案。

推荐的策略：1. 首先搭建地形/地面——可以是平整平面、高度图地形，或是简单的道路/地面工具包网格——这样在放置任何物体之前，就能先确定场景的占地面积和轮廓。
2. 通过`gen_3d_object`生成或挑选单个前景物体（建筑、道具、角色、载具），也可以从引擎的资源库中获取这些物体。
3. 根据任务布局将这些物体放置在基础地面上（出生点、车道、掩体、地标位置）。
4. 将场景视为由地面和实例组成的组合体，而非整个地平线的单一烘焙后的WorldPlay网格。

适用场景：
- 用户描述了某种视觉风格，且不属于室内高保真场景；
- 户外地图、赛车赛道、开阔战场、有天空覆盖的城市街区；
- 布局更多由游戏玩法决定（车道、出生区域），而非基于某张照片还原；
- 需要可编辑/可替换的道具，而非单一的重建外壳。

注意事项：
- 不要将大范围户外参考图输入WorldPlay，还指望它能生成到地平线的连续完整网格——深度拉伸和天空遮挡现象很常见；
- 优先采用明确的地面+物体放置方式，而不要试图仅靠后期滤镜来“修复”开放世界的重建效果。

## 场景构建代码链——先搭灰盒模型，再添加细节
这是“先地面后物体”流程的自动化实现形式。当布局至关重要时——比如游戏玩法空间、已描述的场地、需要在细化前编辑或审核的内容——且你希望在产生生成成本前先确认排列合理性时，就可以使用它。

分为两个阶段，顺序如下：
1. **灰盒阶段**：搭建地形、放置基础几何体并验证。此阶段不会生成任何复杂模型，因此布局有误时直接丢弃也无需额外成本。
2. **细节阶段**：将单个基础几何体替换为生成的网格模型，并设置地面纹理，同时保留灰盒阶段已验证的摆放位置。

五个参数各自独立，因此修改其中一个不会影响其他参数：
| 参数 | 对应`<REPO_PATH>/operators/gen_3d_scene/funcs/terrain_code_edit.py`中的函数 |
|---|---|
| 地形 | `flat`（平整）、`hills`（丘陵）、`slope`（斜坡）、`bowl`（凹地）、`mound`（土丘）、`canyon`（峡谷）；可通过`flattened`（压平）、`levelled_at`（指定高度整平）、`graded`（分级处理）、`carved`（雕刻）、`terraced`（梯田化处理）调整形状，最终通过`baked`（烘焙）定型。 |
| 布局 | `grid_spots`（网格点位）、`ring_spots`（环形点位）、`line_spots`（线性点位）、`scatter_spots`（散点点位）、`clustered_spots`（聚类点位）、`winding_spots`（蜿蜒点位）、`arc_spots`（弧形点位）、`blocks_spots`（块状点位）、`channel_spots`（通道点位）、`spoke_lines`（辐条状线条点位）；可通过`clear_circle`（清除圆形区域内的点位）、`clear_of`（排除特定类型的点位）、`clear_of_ways`（排除道路上的点位）、`in_height_band`（限定在特定高度区间内的点位）、`on_high_ground`（位于高处的点位）、`on_low_ground`（位于低处的点位）、`on_slope`（位于斜坡上的点位）、`fits`（符合特定条件的点位）进行筛选；可通过`crossing`（交叉点）、`chained`（链式排列）、`densified`（密集排列）、`facing`（朝向特定方向）、`highest_spot`（最高点）、`lowest_spot`（最低点）、`contour_radius`（等高线半径）进行测量。 |
| 建筑结构 | `ring_wall`（环形墙）+ `gate_spots`（城门点位）、`arch`（拱门）、`stairway`（楼梯）、`stepped_tower`（阶梯塔）、`ruin`（废墟）、`bridge`（桥梁）、`columns`（柱子）、`road_network`（道路网络）、`interchange`（立交桥）、`water_along`（沿水分布的物体）。 |
| 尺寸设定 | `uniform_sizes`（统一尺寸）、`varied_sizes`（多样尺寸）、`graded_sizes`（分级尺寸）、`tiered_heights`（分层高度）、`stepped_sizes`（阶梯式尺寸）。 |
| 材质设定 | `GREYBOX_MATERIALS`（灰盒默认材质）、`swap_material`（替换材质）、`MATERIAL_TEXTURES`（材质纹理）。 |地形是以一个整体焊接而成的`heightfield`形式呈现的，而非每个区块单独为一个立方体：若采用网格状的立方体排列，每个区块边缘都会形成垂直墙面，从而导致斜坡看起来呈块状。地面形状由`warped_noise`生成，而非正弦波——因为交叉的正弦波会使所有波峰排列在规则的格点上，基于这些格点构建的布局就会呈现成行状；而`warped_noise`会从噪声自身位移后的网格中读取数据，正因如此，斜坡才会呈现出流畅的走势，凹陷处也不会是圆形。`ridged_noise`会将每个八度音阶在零点处折叠，形成相反的轮廓——即狭窄的波峰对应宽阔的凹陷——正是这种特性让山顶能够高出地面，足以支撑灯塔；“`hills(crest=...)`”则结合了这两种噪声效果。

所有地貌最终都要经过`baked`处理：高度数据会被一次性采样并写入网格，后续表面渲染时再通过插值读取。这一过程需要付出一定成本（否则复合地形在每次采样时都需重新计算），同时也是为了确保正确性（这样道具的位置就能依据GLB文件中记载的地面数据进行校验，而非仅依赖导出网格所采样的公式）。

### 模板的两个阶段

`<REPO_PATH>/operators/gen_3d_scene/funcs/terrain_code_template/`目录下有两个文件，二者按功能而非场景划分：

| 文件 | 功能 | 返回值 |
|---|---|---|
| `landforms.py` | 定义地面特征 | 一个`Ground`对象：包含地形信息及从地形中提取的测量数据 |
| `foreground.py` | 定义地面上的物体 | `(terrain, props)` |

地面数据会提供前景物体所需的信息——比如盆地的实际最低点、街道网络的平整高度——因此每项测量数据都只在已知位置采集一次。如果前景物体重复采集这些数据，就会对同一问题给出两个不同的答案。

前景物体也会返回地形信息，因为部分物体会切割其所处的地面：比如小屋下的垫台、平整的轨道。**所有切割操作必须在测量道具位置之前完成**，否则道具会被放置在之后会发生位移的地面之上。

地貌的分类依据是**地貌类型而非层级名称**，因为地形决定了物体的分布规律：盆地中的聚落会聚集在梯田上，山脊上的同一聚落则会顺着高地分布。

| 地貌类型 | 地面特征 | 交通方式 | 地标建筑 | 其他元素 |
|---|---|---|---|---|
| `plains` | 有波纹，两条道路交汇 | 这两条道路 | 瞭望塔 | 驿站、田埂、小树林 |
| `hills` | 有山脊和梯田 | 山顶与凹陷处之间的石堆小径 | 灯塔 | 带院落的农舍、灌木丛 |
| `basin` | 呈凹形且有梯田 | 沿河岸向下的路径 | 湖畔大厅 | 河岸台阶上的小村落、码头 |
| `canyon` | 蜿蜒的河道 | 小径、之字形阶梯 | 峡谷桥 | 营地、岩屑堆、积水区 |
| `walled_town` | 有梯田的土丘 | 城门、街道、入口台阶 | 主堡 | 建筑群、集市广场、城外营地 |
| `city` | 平整的街道、人工开凿的河流 | 街道、桥梁、立交桥 | 立交枢纽与核心塔楼 | 居民区、临街建筑、公园 |从最近的地形开始覆盖，而非凭空构建场景。

有四个要素区分了看似平整的场地与杂乱无章的方块堆，而这里的每个场景都具备这四点特征。在生成任何内容之前，值得用肉眼先加以确认，因为后续添加再多细节也无法弥补缺失的要素：

- **交通流线**：可供通行的路径，无论是铺装路面、台阶、桥梁还是石堆排列而成的路线。没有这条流线的话，所放置的物体就只是摆设而已。
- **地标**：比周围物体更高大、更醒目的事物。灰色方块模型没有纹理和光照效果，因此轮廓是唯一能锚定视觉焦点或赋予场地尺度感的元素。
- **层级结构**：至少包含三种尺寸的物体。如果场地里全是单层方块，无论布局如何，都既不存在前景也无背景。
- **围合结构**：用于划分地面的元素，让开放区域显得是经过刻意设计的，而非随意留下的空白：比如墙壁、树篱、块状物或梯田。

典型的生成流程如下：

```python
from operators.gen_3d_scene.funcs import terrain_code_edit as te
from operators.gen_3d_scene.funcs.terrain_code_template import (
    build_scene, foreground, landforms,
)

scene = build_scene("basin", size=70.0)     # 第一阶段：生成基础配对结构
problems = te.check_scene(scene)            # 继续下一步前必须确保没有问题
te.write_scene(scene, "greybox.glb")

scene = te.swap_mesh(scene, "house-00", "model.glb", height=3.4)   # 第二阶段：替换模型
scene = te.swap_material(scene, "wall", [0.5, 0.47, 0.44])
te.stage_scene_textures(project_dir, scene)
```

若想保留原有地形并重新生成其上的建筑，或者将某个聚落安置在不同形状的地面上，可直接执行这两个阶段的操作：

```python
ground = landforms.hills(size=90.0, relief=5.0)
terrain, props = foreground.plains(ground)      # 默认生成配对结构
scene = te.Scene("mixed", terrain, props)
```

### 值得了解的摆放规则- `ground_under`会将物体放置在**其整个底面所覆盖区域下方的最低地面**上，而非其中心的高度。如果仅以中心点为基准来采样宽基底的高度，那么在斜坡上物体的角落就会悬空。
- `fits`用于测量**候选物体自身旋转后的底面范围**；`clear_of`仅接收一个纯位置信息，无法感知建筑物的宽度。在同时确定物体尺寸和位置时，应使用`fits`。
- `pinned`能在地面下陷时让物体保持在同一水平面——比如桥梁或高架桥面。`sloped`则会让物体沿路径逐渐升高，用于连接两个不同高度的坡道。如果用`pinned`制作的物体来搭建坡道，会形成台阶状结构。
- 铺装路面是由`path_tiles`/`paved`定义的短瓷砖拼接而成的路径，并非一个长条形实体，因此能贴合弯道且随地面起伏。**需将整个铺装网络下方的地面整平至同一水平面**（`graded`）；若相邻铺装块各自独立放置且相互衔接，就会出现缝隙：某块铺装可能比其相邻块高出超过自身厚度，每隔几米就会形成一个坑洼。
- 重塑地面时顺序至关重要：先平整街道，**再**开凿河道。如果顺序颠倒，街道会在每个交叉口处堵塞河道。

**切勿跳过`check_scene`，也不要为了屏蔽它而修改模板。**它会检测超出地形范围的物体、相互重叠的物体、与1.8米高的人体尺寸不匹配的物体，以及会导致导出时两个节点合并的重复ID。那些本应相互接触的物体——比如道路段、墙面装饰、浅水区的芦苇丛——会共享同一个`group`属性从而被排除在外；这是表达物体接触关系的正确方式，而非放宽容差标准。

几何尺寸的测量依据编写者自定义的`<REPO_PATH>/models/common/glb_writer.py`中的`rotated_bounds`和`euler_matrix`参数。如果检测工具采用的旋转或缩放规则与编写者不一致，就会误判磁盘上实际错误的场景为合格。

使用第二阶段功能前需了解以下两点特性：
- `mesh`部件会通过**单一缩放因子**适配其对应的盒状空间，因此仅会填满最长轴向的空间。每当网格形状与被替换的方块不一致时，调用`swap_mesh`时需传入`height=`参数，否则放入宽大基座中的模型会被缩放至与基座等宽。
- 低于零高度的地形（`bowl`、`canyon`）属于地貌类型，并非地形断层。这些区域的瓷砖会向下延伸至统一的底面，从而保证地面结构的完整性。

入口点：
- `python -m operators.gen_3d_scene.funcs.terrain_code_edit` —— 将所有模板导出为GLB格式，并输出检测到的错误数量

## 快速检查清单1. 用户是否指定了场景外观？**否** → 在所选引擎的资源库中搜索可下载且已通过许可审核的场景；记录其来源与许可信息。
2. **是** → 先处理地形/地面，再放置前景物体。对于对布局要求较高的场景，使用*场景构建代码链*：在生成任何内容前先创建简易模型并进行`check_scene`校验。仅当需要处理需要高保真效果的室内/封闭空间时，才采用WorldPlay重建路径，同时需注明该路径属于不稳定方案。
3. 根据任务描述或参考信息，区分封闭场景与开放场景，并采用对应的几何建模策略。
4. 将生成的场景文件写入`<REPO_PATH>/pipeline/common/paths.py`中定义的`3d_scene`路径下。
5. 在接受场景资源前，需目视检查其连续性（封闭场景）或物体在地面上的摆放/缩放情况（开放场景）。对于通过代码生成的场景，`check_scene`必须为空，且录制的全景展示视频需能呈现其所描述的地形特征。
6. 若用户反馈场景质量不一致，需总结此次重建过程的局限性，转而采用“先搭建地面”的构图方式或从资源库选取现有场景，而非反复重新生成场景。
