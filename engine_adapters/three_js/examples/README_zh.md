# three.js 参考游戏玩法包

这些包是基于公共的 `@a3game/playable` 合约构建的可选示例：

| 包名 | 摄像机类型 | 演示内容 |
| --- | --- | --- |
| `fps-example` | 第一人称 | 指针锁定式第一人称移动、射线射击、装弹、准星HUD |
| `arena-fighter-example` | 第二人称 | 固定朝向的决斗移动、轻击/重击、竞技场规则、生命值HUD |
| `racing-example` | 第三人称（跟随视角） | 街机风格车辆操控、加速、手刹漂移、圈数及速度HUD |
| `explorer-example` | 第三人称（环绕视角） | 在高度场上基于摄像机位置的移动、跟随摄像机、蓄力弓、耐力系统 |
| `rts-example` | 俯视视角（正交投影） | 指令驱动的单位、框选操作、平移/缩放机制、战争迷雾、小地图 |
| `motion-vfx-example` | — | 为生成的角色添加动作效果，以及批量处理粒子、光束和拖尾特效 |

## 按摄像机类型而非游戏类型选择示例

**决定游戏代码结构的因素中，摄像机的影响比游戏类型更大。** 采用不同摄像机的两款射击游戏几乎没有任何共通之处；而采用相同摄像机的赛车游戏和探索类RPG，其输入逻辑和摄像机相关模块则完全一致。因此在使用这些示例时，需从需求所指定的视角出发进行适配：- **第一人称视角** — `fps-example`。摄像机就是游戏实体：它依附于玩家枢轴点，瞄准方向直接由输入帧中的偏航角/俯仰角决定，游戏中看不到角色模型。第一人称游戏需要**视图模型**（屏幕角落的武器），而该视图模型是整个项目中被精细处理程度最高的资源——它会占用最大的纹理预算，并使用全分辨率法线贴图。
- **第二人称视角** — `arena-fighter-example`。游戏中有两名格斗者，摄像机负责同时框取两人，移动逻辑被限定在两人连线的轴上。它的特殊性在于摄像机归“对战”本身所有，而非任意一名玩家，因此任何实体都无法移动它。
- **第三人称视角** — 包括`racing-example`（跟随视角）和`explorer-example`（环绕视角）。摄像机是独立物体，会跟随目标移动，因此需要设置延迟效果，且移动必须采用**摄像机相对坐标**：向前移动意味着“远离摄像机方向”，而非“沿角色朝向移动”。这两种子类型的区别在于偏航角的归属——跟随摄像机的偏航角来自载具的航向，而环绕摄像机的偏航角由自身决定，角色会读取该数值。
- **俯视策略类** — `rts-example`。摄像机不属于任何实体：它只是地图的观察窗口，没有任何单位会读取它的数据。这类游戏也是唯一会改变**输入协议**的类型。其他类型采用帧驱动模式——输入帧即玩家的操作意图，一个控制器对应操控一个实体；但这种模式无法支撑五十个以上单位的场景，因为玩家仅有一只鼠标，无法连续发出五十条操作指令。在此类游戏中，输入会产生离散的命令并存储在单位上，这些命令会持续生效直至执行完毕，而`moveX/moveY`则用于平移摄像机。如果你要开发玩家指挥群体而非操控单个角色的游戏，务必先阅读相关内容；小队射击类和城市建设类游戏都存在同样的问题，无论其摄像机类型如何。[`three_js_api.md`](../../../agent_skills/engine_context/three_js_api.md)的第9节对该输入协议有详细说明。

其他所有设定都源于上述选择。`explorer-example`也是了解**非平坦地面行走逻辑**的最佳参考：其中的`terrainHeight`是一个普通函数，既用于可见网格渲染，也用于所有地面查询，只有这种架构才能避免玩家穿过山丘。

这些示例包永远不会自动安装。生成的游戏应在自身的Gameplay Package中适配相关模式，而非依赖或扩展示例包。

`motion-vfx-example`是个特例：它不包含任何游戏内容，仅提供了所有游戏类型都会用到但容易出错的两种模式——对于下载的角色，`assets.tryInstantiate`的用法是正确的，但对于没有骨骼和动画剪辑的生成型角色来说这种做法却是错误的；另外，每个火花对应一个`Sprite`会导致每个火花都需要一次绘制调用。如果你要编写会切换导入美术资源或任何特效的实体，务必先阅读相关内容。每个示例都拥有自己的具体游戏玩法类、生成器、规则以及HUD。`@a3game/playable`仅包含标准化输入、会话、绑定、实体、世界和观测接口。

## 阅读顺序

每个示例会依据“该物体在游戏中代表什么”来命名其模块——这些命名与`test_data/outputs/`目录下生成的游戏所使用的词汇一致，因此无需重命名即可复用相关模式。在生成的游戏中不存在`entity.js`或`factory.js`文件：可操控的物体对应`vehicle.js`/`explorer.js`/`player.js`/`fighter.js`，世界对应`track.js`/`world.js`/`arena.js`/`stage.js`，而生成器则位于`index.js`中，与它所服务的启动函数相邻。

1. `src/<world>.js`——游戏发生的空间。当地面不平整时，需优先阅读此文件，因为此时它属于游戏玩法系统而非单纯场景。
2. `src/<subject>.js`——可操控物体如何实现`A3GameControllableEntity`接口，以及如何将标准化输入帧转换为移动指令。
3. `src/index.js`——游戏的启动流程：加载世界、初始化HUD、设置输入路由、注册生成器、配置摄像机系统。
4. `tests/`——生成游戏的功能验证方式，通过本地运行时桥接而非截图来测试。

`explorer-example`与`test_data/outputs/game_archer_explorer`的模块结构完全一致：`world.js`、`explorer.js`、`arrow.js`、`index.js`。

`arena-fighter-example`早于这一规范制定，仍使用`entity.js`/`factory.js`；应以`explorer-example`为参考模板。

`rts-example`将步骤2拆分，按指令驱动：`commands.js`（定义指令内容）、`unit.js`（单位执行指令的方式）以及`selection.js`（接收指令的对象）。需先阅读`commands.js`。

## 测试

`arena-fighter-example`、`explorer-example`和`rts-example`均在`tests/`目录下提供测试规范文件。示例本身不自带测试运行器；插件的配置已包含`../../examples/**/tests/**/*.spec.js`，因此可随框架套件一同运行：

```bash
cd engine_adapters/three_js/plugin/A3GamePlayable && npm test
```

这些测试利用模拟DOM事件，针对真实的会话/运行时接口验证游戏玩法逻辑，并不涉及WebGL输出或浏览器实际游玩测试。

`rts-example`的范围限定为实时连续位置控制，采用开放地形与直接转向机制——并非路径查找或群体避让算法，网格辅助功能仅用于放置操作。雾效会遮蔽地形，并在渲染、瞄准及小地图中隐藏敌方单位；不存在地形遮挡、最后可见标记系统、经济系统或网络指令协议。运行时快照为完整的诊断状态，而非经过雾效过滤的客户端消息。摄像机系统会限制视野范围，而非覆盖整个视图区域。导入的世界需匹配地面查询参数。

## 将其作为起点进行安装

```python
from engine_adapters.three_js import ThreeClient
``````python
three = ThreeClient(project_path="/path/to/project")
three.plugin.install(
    {
        "game_id": "my_game",
        "run_id": "default",
        "task_kind": "mechanic",
        "task_id": "gameplay_package",
    }
)
```

`plugin.install` 用于指定仓库中的任务标识，而非该目录内的文件路径。手动复制示例会绕过注册表以及 `plugin.install` 所执行的依赖同步机制。
